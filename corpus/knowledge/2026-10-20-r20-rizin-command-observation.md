## Shell and chaining boundary

The Rizin Handbook (S044) documents `;` as a command separator (§8.0.5), consistent with the observed successful `iI; iS`; it documents `!<command>` as a shell command run with `system(3)` (§8.0.2), not as a refused escape. REA 6.5.0's contract likewise warns that caller-selected Rizin commands/plugins can execute foreign code, mutate files, access the network, or read outside the carrier (S040; `.ufo/waves/round-20/evidence/c2/rizin-pe/rea-cli-source-notes.md:9`); its only input rule is "no CR/LF/NUL" (wave-1 `ScoutRizinSchema.md`, `domain/reverseEngineering.js:23-30`). This leg therefore did not attempt `!echo`. A wave-1 scout reported in its seat report that `!echo` ran and that `;` did **not** chain in its own captures under `/tmp` (not retained in the lane); the retained `06-semicolon-chain` record contradicts the `;` part, so the scout's chaining statement is rejected and its shell-escape statement is treated as unretained, consistent with S044. Treat `execute-rizin-command` as an unrestricted shell-capable surface: run only read-only info commands on hash-pinned carriers.

Caps (S040, wave-1 `ScoutRizinSchema.md`, source-read): 120000 ms deadline and 16 MiB combined stdout+stderr are hardcoded; neither was reached by any retained call here.
