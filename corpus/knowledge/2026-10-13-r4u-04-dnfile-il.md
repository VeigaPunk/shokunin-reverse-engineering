# kaidoku-r4u / 04 — REA + dnfile/dncil as one held managed surface

Round-4-unlock consolidation: prove `rea-agents@6.4.0` managed verbs and the
pure-Python dnfile+dncil path work **together** on the same corpus — REA as
the evidence-grade metadata/identity layer on small i386-AnyCPU assemblies,
dnfile+dncil as the unbounded IL layer that covers every assembly REA's
fixed 64 MiB representation budget or 0xfd1d machine gate refuses. Built on
the r4 lane-11 unlock (`kaidoku-r4/11-managed-unlock.md`); fresh venv
`/tmp/dnfenv-r4` (uv, CPython 3.13.16, dnfile 0.18.0 + dncil 1.0.2 + pefile
2024.8.26).

## Candidate: dnfile+dncil — covers what the 64 MiB budget cannot

- claim: the lane-11 recipe reproduces identically on the fresh 3.13 venv
  and decodes Pinta.Core.dll — the exact assembly REA just refused —
  completely: machine 0x014c, flags CLR_ILONLY, EntryPointTokenOrRva
  0x00000000 (library → no entry point), 380 TypeDefs / 2 766 MethodDefs /
  14 417 rows across 17 counted tables; dncil disassembled **2594/2594**
  non-empty method bodies (172 rva-0 abstract/pinvoke rows correctly
  skipped), 54 893 CIL instructions total, largest body a `MoveNext` state
  machine (578 instrs). Entry-point resolution demonstrated on Pinta.dll
  (174 080 B, also under REA's byte band but shown for the mechanic):
  CLI header token `0x0600007a` → MethodDef row 122 `Main`, owner resolved
  by walking TypeDef.MethodList ranges → `Pinta.MainClass`; its 650/650
  bodies decoded too (17 523 instrs). Cost: zero budget, zero SDK, ~15-line
  RVA shim, pure Python.
- source: `/tmp/dnfenv-r4/bin/python /tmp/ilcensus.py
  /usr/lib/pinta/Pinta.Core.dll` and `…/Pinta.dll` (outputs above).
- verify: rebuild =
  `uv venv /tmp/dnfenv-r4 --python 3.13 &&
   uv pip install --python /tmp/dnfenv-r4/bin/python dnfile dncil`;
  the shim is a `CilMethodBodyReaderBase` subclass with `read(n) →
  pe.get_data(rva+pos, n)`, `tell() → pos`, `seek(off)`; feed
  `CilMethodBody(RvaReader(pe, methoddef_row.Rva))` and iterate
  `.instructions`. Entry token: `pe.net.struct.EntryPointTokenOrRva`
  (field name in dnfile 0.18 — NOT `EntryPointToken`); table =
  token>>24, row = token&0xffffff; 0x06 = MethodDef.
- verified-at: 2026-10-13
- suggested: admit — this is the complementarity proof: REA's refusal
  surface (14 large assemblies ≥ ~220 KB + 181 0xfd1d assemblies) is fully
  inside dnfile's acceptance surface. Held-surface routing rule: try REA
  verbs first for envelope-grade evidence (evidence ids, sha256, MVID,
  classification) on 0x14c/0x8664 assemblies; fall to dnfile+dncil for IL
  on everything else and whenever `coverage.state` ≠ complete.

## Summary
Managed analysis is now a **held two-layer surface**, not a blocked
frontier. Layer 1 (REA 6.4.0): `inspect-managed-artifact` gives
evidence-grade identity/PE/CLI/metadata envelopes on every 0x14c assembly
(all Pinta dlls; re-verified end-to-end on Pinta.Docking.dll,
ev_2fb95e…) and on 0x8664, refusing only 0xfd1d;
`inspect-managed-members`/`-native-boundaries` return complete metadata +
member census under the hardcoded 64 MiB representation budget (pass
≤ ~205 KB; Pinta.Docking came back `partial` solely on GENERICINST
signature forms, `unavailable` only when the budget trips — Pinta.Core,
408 KB). Layer 2 (dnfile 0.18 + dncil 1.0.2, ~15-line RVA shim, fresh
`/tmp/dnfenv-r4`): unbounded full-IL decode with zero machine gate —
2594/2594 bodies / 54 893 instructions on the very Pinta.Core.dll REA
refused, entry-point resolution proven (`Pinta.MainClass.Main`, token
0x0600007a). Routing rule for downstream lanes: REA first for envelope
evidence where accepted; dnfile+dncil for IL everywhere and as the sole
path on 0xfd1d and budget-overflowed assemblies. The r1 "rejects AnyCPU"
characterization stays corrected: the gate is the COFF machine allowlist
plus the 64 MiB members budget — both now mapped, both now covered.
