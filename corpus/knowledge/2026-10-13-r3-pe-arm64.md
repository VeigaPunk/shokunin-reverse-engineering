# 08 — PE subtype: ARM64 (round 3)

Round 2 proved x86-64 PE via Ghidra. This round re-runs the same three-operation
chain (analyze → search procedures → decompile) against a small ARM64 PE to close
the PE-subtype gap.

## Candidates

### Candidate 1 — setuptools `cli-arm64.exe` (selected)

- **claim:** `cli-arm64.exe` is a PE32+ ARM64 Windows executable that the REA
  Ghidra provider can analyze, enumerate procedures on, and decompile.
- **source:** `/home/vgpnk/.cache/uv/archive-v0/M1E0QXq07p7Gx3Fp/setuptools/cli-arm64.exe`
  (13,824 bytes; setuptools entry-point launcher bundled in uv's cache).
- **verify:**
  - Identity: `sha256sum` → `b9a7d08da880dfac8bcf548eba4b06fb59b6f09b17d33148a0f6618328926c61`;
    `file` → `PE32+ executable for MS Windows 6.02 (console), ARM64, 6 sections`;
    `llvm-readobj --file-headers` → `Machine: IMAGE_FILE_MACHINE_ARM64 (0xAA64)`,
    `AddressOfEntryPoint: 0x1E10`, `ImageBase: 0x140000000`.
  - `analyze --format json`: provider chain `rea-workflow` → `ghidra` 12.1.4,
    `architecture: "arm64"` (auto-from-header), `available_architectures: ["arm64"]`.
    Result: `segment_count: 7` (Headers, .text, .rdata, .data, .pdata, .rsrc,
    .reloc), `procedure_count: 136`, `string_count: 77`. No typed failure.
  - `search --kind procedures --mode regex '.*'`: full 136-entry list returned;
    `entry` resolves at `0x140001e10` (ImageBase + 0x1E10, matching the PE
    header). Named ARM64/MSVC bodies include `__security_push_cookie`,
    `__security_pop_cookie`, `_guard_dispatch_icall`, `_guard_check_icall`,
    plus resolved KERNEL32/CRT/VCRUNTIME140 import thunks.
  - `decompile entry`: returned clean pseudocode with zero decompiler
    limitations: `DWORD entry(void)` → calls `FUN_140002178()` then returns
    `FUN_140001c60()`.
  - ARM64-specific notes: `.pdata` (512 B ARM64 unwind data) parsed as its own
    segment; the `native_aot_metadata.contract_revision` string still reads
    `rtr-9.1-x64-pe-read-only-v3` while `architecture` correctly reports
    `arm64` — cosmetic naming only, not a mis-detection. Ghidra default
    analyzer preset handled ARM64 without fallback or error.
- **verified-at:** 2026-10-13T15:43Z
- **suggested:** mark ARM64 PE as **held** (same coverage class as x86-64 PE).
  Next frontier for the PE axis is not another machine type but depth: a
  larger ARM64 binary with jump tables / ARM64X hybrid PE, or exception-heavy
  code exercising `.pdata` unwind recovery.

## Run log

- `find ~/.cache/uv -name '*arm64*.exe' -o -name 'gui-arm64.exe' -o -name 'cli-arm64.exe'` → found `setuptools/cli-arm64.exe` and `setuptools/gui-arm64.exe`.
- `sha256sum`, `file`, `llvm-readobj --file-headers` on `cli-arm64.exe` → ARM64 (0xAA64), 6 sections, entry 0x1E10 — confirmed target.
- `timeout 900 npx -y rea-agents@6.4.0 analyze cli-arm64.exe --format json` → success, evidence `ev_f4e02f93…`; 7 segments / 136 procedures / 77 strings.
- `rea-agents search cli-arm64.exe --kind procedures` → invalid_input (pattern required); retried with `--mode regex --pattern '.*'` → success, evidence `ev_d0069932…`; `entry` at 0x140001e10 plus all named thunks/imports.
- `rea-agents decompile cli-arm64.exe entry --format json` → success, evidence `ev_93ada8d1…`; pseudocode returned, `limitations: []`.
- No Ghidra choke, no typed failure, no fallback provider.

## Summary

**ARM64 PE held.** The full analyze → search → decompile chain works on the
0xAA64 setuptools launcher under Ghidra 12.1.4 with the default analyzer
preset — 7 segments, 136 procedures, entry-point resolution matching the PE
header, and clean `entry` pseudocode. The PE subtype axis now covers both
x86-64 (round 2) and ARM64 (round 3). Remaining PE frontier is scale/shape
(ARM64X hybrid binaries, jump-table density, .pdata unwind edge cases, the
91 MB Godot template), not machine coverage.
