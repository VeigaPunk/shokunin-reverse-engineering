# 05 — wakaru OOM gate: root-caused and fixed (round-4-unlock)

Axes: reachability (`recover-javascript-sources` went from
`capability_unavailable` to a successful first-ever run), correctness of
diagnosis (exact REA spawn chain + limit identified, not guessed), fix
minimality (one env-var retarget; no patches, no wrappers, no upstream
change needed), determinism (native path is immune to the ASLR-dependent
flake band the node shim exhibits).

## Candidate: ROOT CAUSE — REA wraps `REA_WAKARU_COMMAND` in `prlimit --as=1 GiB`, and the host's `wakaru` is a two-hop Node.js shim that cannot initialize V8 under 1 GiB

- claim: REA never spawns the configured command directly.
  `runWakaruCommand` invokes
  `spawnOwnedProviderProcess({command: context.limiter, arguments:
  ["--as=<addressSpaceBytes>", "--fsize=<outputBytes>", "--core=0",
  "--cpu=120", "--", context.command, ...context.arguments]})`. `context.limiter`
  is `REA_JAVASCRIPT_PRLIMIT_COMMAND ?? "/usr/bin/prlimit"` and
  `addressSpaceBytes` is the hardcoded `1024*1024*1024`. Child env =
  full host env merged with `{TMPDIR: <tmpdir>, RAYON_NUM_THREADS: "1",
  NO_COLOR: "1", REA_PROCESS_RUN_ID: <runId>}` — no NODE_OPTIONS
  injection, no worker `resourceLimits`, no seccomp; the only constraint
  is `prlimit` RLIMIT_AS/FSIZE/CORE/CPU. The probe that OOMs is the
  literal spawn
  `/usr/bin/prlimit --as=1073741824 --fsize=134217728 --core=0 --cpu=120
  -- <REA_WAKARU_COMMAND> --version` (`WakaruExecution.js` line 29-32
  runs `["--version"]` through the identical wrapped path before the real
  unpack run).
- On this host the configured command is the npm `wakaru` package =
  `#!/usr/bin/env node` alias shim
  (`.../node_modules/wakaru/bin/wakaru`) that `spawnSync`s
  `process.execPath` on `@wakaru/cli/bin/wakaru`, which is itself a node
  shim that `spawnSync`s the real native ELF
  `@wakaru/cli-linux-x64/wakaru`. The FIRST hop dies inside
  `v8::Isolate::Initialize` → `v8::base::FatalOOM` — "Failed to reserve
  virtual memory for CodeRange" — because Node v24.21.0 needs a >1 GiB
  virtual reservation for the V8 code range/cage at isolate init.
  `wakaru --version` standalone only works because no RLIMIT_AS is set;
  `ulimit -v 2GiB` clears the needed reservation, `1 GiB` does not.
- source:
  `~/.npm/_npx/9b9809298fe40d2c/node_modules/rea-agents/dist/javascript/recovery/WakaruCommand.js:43,60-79`
  (limiter resolution + spawn args + env),
  `.../dist/javascript/recovery/WakaruRelease.js:26`
  (`addressSpaceBytes: 1024*1024*1024`),
  `.../dist/javascript/recovery/WakaruExecution.js:29-32` (`--version`
  probe through same wrapper),
  `.../dist/process/ProviderProcess.js:18-44` (`{...hostEnvironment,
  ...options.env, REA_PROCESS_RUN_ID}` + `spawn(shell:false,
  detached:true)`); host side: `readlink -f $(which wakaru)` →
  `/home/vgpnk/.local/share/fnm/node-versions/v24.21.0/installation/lib/node_modules/wakaru/bin/wakaru`
  (file content read: `spawnSync(process.execPath, [binPath, ...])`);
  `~/.bashrc:63` `export REA_WAKARU_COMMAND="$(command -v wakaru)"` —
  binds the node shim, not the ELF.
- verify: `prlimit --as=1073741824 --fsize=134217728 --core=0 --cpu=120
  -- wakaru --version` → Fatal OOM "Failed to reserve virtual memory for
  CodeRange", stack in `v8::Isolate::Initialize`; 5/5 deterministic FAIL
  at 1 GiB. Minimal wakaru-independent repro: `prlimit
  --as=1073741824 -- node -e '1'` → same FatalOOM, 5/5 FAIL, while `node
  --version` passes (it never initializes an isolate).
- verified-at: 2026-10-13 r4u lane (shells 70e984, fb3ebc, 04fa36 —
  `node -e` 5/5 SIGTRAP-core FAIL; `node --version` 3/3 OK).
- suggested: admit — mechanism is fully identified; no env-leak,
  worker-limit, or seccomp factor exists in the spawn path.

## Candidate: FIX — point `REA_WAKARU_COMMAND` at the native ELF already inside the npm install (`@wakaru/cli-linux-x64/wakaru`); end-to-end `recover-javascript-sources` succeeds under REA's real limits

- claim: `@wakaru/cli` delegates to optional platform packages; on
  linux-x64 the installed tree already contains a real 26,793,296-byte
  stripped ELF at
  `/home/vgpnk/.local/share/fnm/node-versions/v24.21.0/installation/lib/node_modules/wakaru/node_modules/@wakaru/cli-linux-x64/wakaru`.
  Pointed there, the exact REA probe
  `prlimit --as=1073741824 --fsize=134217728 --core=0 --cpu=120 -- <ELF>

## Candidate: flake band characterization — node shim is nondeterministic near ~1.1–1.25 GiB, deterministic below/above

- claim: bisecting `--as` for the node-shim chain: deterministic FAIL at
  ≤1 GiB (5/5, SIGTRAP core dump) and at ~1.09 GiB; an ASLR-dependent
  interleaved OK/FAIL band roughly 1.13–1.25 GiB (observed OK at
  1.125G, FAIL at 1.156G, OK at 1.187G, FAIL at 1.219G, then OK at 1.25G
  and everything ≥1.25G through 6G). The flake is V8 cage placement vs
  the reservation window — even if REA's limit were bumped slightly the
  node path stays unreliable; the native ELF has no such band (clean
  from 256 MiB up).
- source: `for lim in …` bisect runs, outputs captured in lane shell
  815882 (≥2G all OK) and fb3ebc (interleaved band) and 04fa36 (native
  floor).
- verify: `for lim in 1153433600 1207959552 1241513984 1275068416
  1308622848 1342177280; do prlimit --as=$lim -- wakaru --version; done`
  — repeat to reproduce the interleaving.
- verified-at: 2026-10-13 r4u lane (shells 815882, fb3ebc).
- suggested: admit as boundary evidence — explains why earlier context
  saw `ulimit -v 2GiB` pass while REA's 1 GiB fails, and why a marginal
  bump would be a trap.

## Candidate: alternates tested/considered — all Pareto-worse than the native-ELF retarget

- claim (a): `NODE_OPTIONS=--jitless` under `--as=1GiB` makes the node
  shim pass (`wakaru 1.14.0`) — jitless skips the CodeRange reservation.
  But REA merges host env into the child, so the flag would have to be
  exported on the whole REA process or hidden in a `REA_WAKARU_COMMAND`
  wrapper script; keeps two node hops per probe and jitless-slows any JS
  in the chain. Strictly worse than zero node hops.
- claim (b): `REA_JAVASCRIPT_PRLIMIT_COMMAND` is a supported override
  (`WakaruCommand.js:43`) validated only as absolute/X_OK/regular-file —
  a shim rewriting `--as=1073741824` to a higher value before exec'ing
  `/usr/bin/prlimit` would mechanically work, but raises the provider's
  documented 1 GiB ceiling (`RECOVERY_LIMITATIONS` text ships that bound
  to users) and still rides the flaky band's edge; unnecessary now.
- claim (c): pointing `REA_WAKARU_COMMAND` at `@wakaru/cli/bin/wakaru`
  directly (skipping the meta shim) still runs `node` — same CodeRange
  death at 1 GiB.
- source: `prlimit --as=1073741824 -- env NODE_OPTIONS=--jitless wakaru
  --version` → `wakaru 1.14.0` (shell 745ff1); source reads cited above.
- verified-at: 2026-10-13 r4u lane (shell 745ff1).
- suggested: record as fallbacks only; do not adopt.

## Upstream-boundary report (precise, for the record)

- REA spawn context (rea-agents@6.4.0, all three npx cache copies
  identical version): `spawn(<REA_JAVASCRIPT_PRLIMIT_COMMAND ??
  "/usr/bin/prlimit">, ["--as=1073741824","--fsize=134217728","--core=0",
  "--cpu=120","--",<REA_WAKARU_COMMAND realpath'd>,<args>], {shell:false,
  detached:true, env:{...process.env,TMPDIR,RWT,NO_COLOR,
  REA_PROCESS_RUN_ID}})`; `resolveWakaruCommand` requires linux/x64,
  absolute path, R_OK|X_OK, sha256 fingerprint re-verified post-run.
- Minimal failing repro (host-independent):
  `prlimit --as=1073741824 -- node -e '1'` on Node v24.21.0 linux-x64 →
  `Fatal process out of memory: Failed to reserve virtual memory for
  CodeRange` at `v8::Isolate::Initialize`. Any JS-entrypoint "binary"
  (node shim, pkg/SEA, bun-built-against-V8) is incompatible with the
  hardcoded 1 GiB ceiling; the upstream `wakaru` npm meta-package wires
  exactly such a chain. Boundary is thus: REA's contract is sound —
  "Linux x64 binary" means the ELF in `@wakaru/cli-<platform>`; the
  host's `.bashrc` bound the wrong artifact. Optional upstream doc nit:
  REA's `docs/javascript-recovery.md#install-wakaru` could warn that the
  npm `wakaru` wrapper is a node shim, not the binary operand.

## Summary

**wakaru is REACHABLE — gate fixed and verified end-to-end, not merely
bounded.** Root cause is a two-layer mismatch: (1) REA hardcodes
`prlimit --as=1073741824` (1 GiB RLIMIT_AS) around whatever
`REA_WAKARU_COMMAND` names, and (2) the host bound that var
(`.bashrc:63`) to the npm `wakaru` meta-package — a `node`-shebang alias
shim that spawnSyncs a second `node` shim before ever reaching the real
binary. Node v24.21.0 cannot initialize a V8 isolate under 1 GiB
address space (CodeRange reservation → `FatalOOM`, minimal repro
`prlimit --as=1073741824 -- node -e '1'`, 5/5 deterministic). The fix is
retargeting the env var to the native ELF already installed at
`wakaru/node_modules/@wakaru/cli-linux-x64/wakaru`: under REA's literal
probe args it prints `wakaru 1.14.0` (works down to 256 MiB, no flake
band — the node chain is ASLR-flaky across ~1.13–1.25 GiB), and
`recover-javascript-sources` produced a complete Evidence envelope
(`ev_5cb1856a64b42f36f5a4f974f495d92f259d5fc243c6b575fe2594e45a463957`,
probe and unpack both exit 0). Operator action: replace `.bashrc:63`
with the `@wakaru/cli-linux-x64` path (fnm-versioned — prefer the
`find $(npm root -g)` resolver or a stable copied binary). No REA patch,
no limiter shim, no upstream change required; alternates (`--jitless`
env, `REA_JAVASCRIPT_PRLIMIT_COMMAND` rewrite shim) verified working but
Pareto-worse.
