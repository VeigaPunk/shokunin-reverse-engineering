## What REA does with a carrier

[observation] The harness runs REA 6.5.0 `extract-firmware` as `npx -y rea-agents@6.5.0 extract-firmware --format json --full-output --max-depth 1 --max-output-bytes 536870912 --max-output-files 100000 <carrier> <outdir>` (the byte and file budgets are frozen in `tools/round-50/carriers.json` under `rea_parameters`; the counter replays the receipt's own parameters). [observation] unblob 26.6.4 is the provider's extractor, `sasquatch` 4.5.1 is on the child `PATH`, and the LE argv is `sasquatch -le -no-exit-code -f -d <outdir> <inpath>` (S245 :53-54); no `-be` binary is needed for an LE body. [observation] The chunk is named `squashfs_v4_le`; a chunk is failed only when the provider records an extraction report, so the missing-extractor case is visible as a `missing-extractor-dependency` gap rather than as a different handler name. [observation] REA stages the input as `firmware.bin`, so the chunk's extract root is the `…_extract` directory of the chunk; every oracle path is compared by **equality after mapping into that root**, never by suffix. [observation] In the pre-freeze 7530 probe 281 of 282 kept-symlink target values differed from the oracle, so the counter compares symlink rows by path and kind, not by target text; the retained receipts do not establish a universal rewrite rule. [observation] unblob passes `-no-exit-code` to `sasquatch`, which turns a non-fatal extractor failure into exit 0 and no gap; a partially failed extraction is therefore visible only through the oracle comparison, which is why the counter requires every oracle file to be published. [inference] The round-41 gap-rule derivation's statement that the removed-symlink set depends on readdir order is carried as inference, not as an observation of these runs. [observation] The default 10 000-entry staging limit failed on the pre-freeze 7530/7590 probes (13.4k files); no default-budget run was attempted on the four final carriers, whose recorded runs used the frozen 100 000-entry budget.

## The marker is a constant of the pinned bytes, not a proof of origin

[observation] unblob 26.6.4 tests `mkfs_time == bytes_used` only inside its **big-endian** v4 branch (S245 :48); every little-endian v4 member takes `sasquatch -le -no-exit-code -f -d …` under that pinned handler, marker or not, so an AVM-marker LE member and a standard LE member take one handler and one argv (a host-built standard LE image and its twin with `mkfs_time` patched to `bytes_used` produce the same REA projection). [observation] The marker is re-stampable: the round-50 W1 experiment wrote `mkfs_time = bytes_used` (a 4-byte patch at superblock offset 8) on standard-LE xz fixtures and REA produced identical projections for the patched and unpatched bodies; no stock-`mksquashfs` invocation was run, so only the patch experiment — not a stock CLI build — is evidenced. [inference] The marker adds **no** evidence of origin once the carrier sha256 holds; `layout_ok` in the counter is a frozen-layout statement about the pinned bytes, and it is kept as the second red for a planted standard LE carrier (CTL-C1-4 is red on `carrier_pin_ok` **and** on `layout_ok`). [observation] "Genuine" in this entry means provenance — the sha256 chain from the vendor URL — and not the marker. [observation] No source text in the registry describes an LE AVM layout: the Freetz documents define the big-endian variant, patch 101 adds only the `AVM_LE` byte-order symbol (S243), and the marker-writing code branch (`550-TARGET_FORMAT__AVM_BE_AVM_LE.patch`) is a Freetz build option that the shipped Freetz build never compiles. [observation] One uncatalogued Freetz wiki page states the same relation for AVM-LE ("The only difference of this format to the original LE format is that the value of the mkfs_time superblock field is equal to the bytes_used field", `https://www.freetz.mhampicke.de/trunk/make/squashfs4-le/Config.in`, read 2026-10-28); the lane holds no `corpus/SOURCES.md` row for it, so it is cited here as prose and not as a `source:` row.

## Limits (the seven disclosed limits of R50-C1, restated)

1. [observation] The marker is invisible to unblob and re-stampable. The claim is "REA publishes every oracle file of these four pinned vendor members", not "REA or unblob recognises AVM"; a standard LE image takes the same handler (the round-36 Core). No registered `corpus/SOURCES.md` row cited by this entry describes an LE AVM layout — patch 101 (S243) adds only the symbol and byte order, and the uncatalogued Freetz wiki passage quoted above is prose, not a row — so the marker is an empirical property of the four carriers and of all 28 census rows.
2. [observation] Vendor bytes are fetched, never committed. An image AVM replaces makes the chain unfetchable (the four are the final or long-standing releases of their models, not a guarantee), and the counter-time rerun is unrunnable without a `--carrier-cache`. The committed receipts and oracle tables are the durable evidence.
3. [observation] A relabelled replay of genuine receipts scores the same as a fresh run on the receipt side, which is why the counter's own rerun is the measurement (inherited from round 49).
4. [observation] The documentation bindings are presence checks: a `PROVINCE.md` Core row naming `squashfs_v4_le` and the AVM marker, a `Round-50 frontier note` line, the entry itself, `corpus/README.md`'s coverage-map row and the `SOURCES` rows' `used-by` cells.
5. [observation] Four carriers, one vendor, xz only, depth 1: this is not "every LE AVM image". The SoC lines are not self-described by the images (the cable boxes' x86 member names its architecture by path only).
6. [observation] REA's 120 s `provider_timeout` is a host-load property. The rerun repeats up to 3 times on a timeout only; a persistent timeout is exit 2, never a pass.
7. [observation] The oracle rows for symlinks compare path and kind, not `link_target` (unblob rewrites targets), and the set of removed `MaliciousSymlinkRemoved` links depends on readdir order, so the rule is set-agnostic.
