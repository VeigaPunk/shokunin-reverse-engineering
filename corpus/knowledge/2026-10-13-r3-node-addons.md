# kaidoku-r3 · 11-node-addon — ASAR↔native fringe: `.node` addons through REA

Axes: **fringe-coverage** (every `.node` under `*.asar.unpacked` on the host enumerated and fingerprinted), **linkage-taxonomy** (how each addon binds N-API — two distinct families found), **REA-fidelity** (does the Ghidra pipeline give usable decomp on a shared-object addon, incl. symbol/PLT resolution and the nm→Ghidra address map), **evidence-quality** (every claim carries a rerun-able command). Primary deep-dive target: `btime/binding.node`; `get-fonts` surveyed with stock tools; signal/1Password modules fingerprinted for the taxonomy.

## Candidate: The host Electron executable is the N-API provider — no `libnode.so` is needed
- claim: Neither addon declares `libnode` in DT_NEEDED. `btime` NEEDED = `libstdc++.so.6, libgcc_s.so.1, libc.so.6`; `get-fonts` adds `libfontconfig.so.1`. The 36/39 undefined `napi_*`/`node_api*` imports (btime/get-fonts resp.) resolve at `dlopen()` time against the loading process's own dynamic exports: `/usr/lib/electron43/electron` and `/usr/lib/signal-desktop/signal-desktop` each export **145 `T napi_*`** plus **14 `node_api*`** symbols in `.dynsym`. That is the whole loading contract: Electron statically embeds Node and re-exports the N-API surface globally; the addon just needs matching undefined refs.
- source: `readelf -d` both addons; `nm -D <addon> | grep ' U napi'`; `nm -D /usr/lib/electron43/electron | grep -c ' T napi_'` → 145 (same count for signal-desktop's bundled binary)

- suggested: admit — key fringe fact: a `.node` is *not* self-contained; its N-API undefineds are satisfied by whatever Electron binary loads it. Versioning of the napi surface lives in the host, not the addon (which is why `node_api_module_get_api_version_v1` exists).

## Candidate: C++ `node-addon-api` registration pattern — `napi_register_module_v1` → `Init` → `napi_create_function` → `napi_set_property`
- claim: Both addons export the standard pair `napi_register_module_v1` (the dlopen entry Electron calls) and `node_api_module_get_api_version_v1`. Disassembly shows `napi_register_module_v1` tail-calls `Init(Napi::Env, Napi::Object)` (`_Z4InitN4Napi3EnvENS_6ObjectE`), which `operator new`s a `Napi::details::CallbackData` wrapper, calls `napi_create_function` with the C++ callback (`_Z5btimeRKN4Napi12CallbackInfoE` / `_Z8getFontsRKN4Napi12CallbackInfoE`), builds the export name via `napi_create_string_utf8` (`"btime"` @ file-0x8138, `"getFonts"` @ file-0x8158) and attaches it with `napi_set_property(exports, name, fn)`. `package.json` pins `node-addon-api 6.1.0`; modules are *not stripped*, so mangled C++ names demangle cleanly (`nm -D`, `c++filt`).
- source: `nm -D` on both; `objdump -d --disassemble='napi_register_module_v1'/'_Z4Init...' -M intel`; `strings -a -t x`; addon `package.json`/`index.js`
- verify: `objdump -d --disassemble='napi_register_module_v1' -M intel /usr/lib/obsidian/app.asar.unpacked/node_modules/btime/binding.node | grep call` → single tail `call Init`
- verified-at: 2026-10-13 12:45 -03
- suggested: admit — this is the canonical "what a N-API addon looks like" fingerprint: two registration exports + one `Init` + `napi_create_function`/`napi_set_property` sequence + C++ `Napi::` vtables/typeinfo in `.data.rel.ro`. Any lane can identify the JS-visible export set from `(napi_create_function callsite, napi_create_string_utf8 arg)` pairs alone.

## Candidate: `btime` semantics — JS shim validates, native is a thin `utimes`-family wrapper; Linux path is a JS no-op
- claim: `index.js` does all real validation (`assertPath` rejects non-string/empty/NUL-containing paths; `assertTime` bounds to uint ≤ 2⁴⁸−1; `pathBuffer` builds a NUL-terminated Buffer via `path._makeLong`). The native `btime(buffer, seconds)` callback re-checks argc==2, `napi_is_buffer(arg0)`, `napi_typeof(arg1)==3` (napi_number), pulls the bytes via `napi_get_typedarray_info`, the number via `napi_get_value_int64`, calls `set_btime(path,sec)` (exported `_Z9set_btimePKcm`), and returns the status as `napi_create_double`. On `linux` the JS wrapper returns early — "Linux does not support btime" — so the native export is dead code on this host (still shipped in the linux build). `get-fonts` instead runs a `FontWorker : Napi::AsyncWorker` subclass (`_ZN10FontWorker7ExecuteEv`) with `napi_create_promise`/`napi_queue_async_work`, calling `FcInit`/`getAvailableFonts` against DT_NEEDED `libfontconfig.so.1` — i.e., Obsidian enumerates system fonts off-thread through fontconfig.
- source: `index.js` of both addons; `nm -D`; `objdump`/`strings` (`"bad arguments, expected: (buffer path, seconds btime)"` @ 0x8268, `fontsLinux.cc`, `FcInit`); REA decompile below
- verify: `grep -n 'platform\|btime' /usr/lib/obsidian/app.asar.unpacked/node_modules/btime/index.js`; `nm -D get-fonts/binding.node | grep -E 'FontWorker|napi_create_promise|napi_queue_async'`
- verified-at: 2026-10-13 12:45 -03
- suggested: admit — shows the fringe split: the `.unpacked` tree must carry BOTH the `.js` shim and the `.node`; auditing one without the other misreads which side owns validation (here: JS owns checks, native owns the syscall — and on Linux the native half never runs).

## Summary
The ASAR↔native fringe on this host is 7 `.node` files under 3 `*.asar.unpacked` trees (obsidian, signal-desktop, 1Password) spanning 50 KB–188 MB. Every one is a plain `ET_DYN` ELF whose N-API contract is satisfied by the *loading Electron executable* (145 exported `napi_*`), never a `libnode.so` dependency — which is exactly why ASAR must unpack them to the filesystem for `dlopen`. Two linkage families: classic C/C++ `node-addon-api`/N-API modules carry dozens of undefined `napi_*` imports; Rust napi-rs/Neon modules (libsignal, ringrtc, 1Password) carry zero and bind through `dlopen`/`dlsym`, still exporting `napi_register_module_v1` plus descriptor-table `D` symbols. The registration fingerprint is uniform: `napi_register_module_v1` → `Init` → `napi_create_function` + `napi_create_string_utf8` + `napi_set_property`. REA 6.4.0 handles the format end-to-end with no special casing — analyze (ephemeral Ghidra 12.1.4), procedure search (PLT+def hits), and a coherent decompile of `btime` showing the full argc→`napi_is_buffer`→`napi_get_typedarray_info`→`set_btime`→`napi_create_double` flow; the only operational rule learned: Ghidra image base is 0x100000, so nm/ELF vaddrs need +0x100000 before feeding REA. Bonus semantic finding: obsidian's `btime` is a JS-validated, Linux-dead `utimes` shim; `get-fonts` is an async fontconfig enumerator (`FontWorker`/`napi_create_promise`/libfontconfig).
