# E27 (executor) — adversarial read: are the two reruns REALLY byte-identical in request?

Scope: read-only comparison of the two r10 rerun legs against the r7 / r6 originals.
No process was signalled; no repo file was edited except this report. Scratch: none needed
(all evidence read in place under `/var/tmp/arc2-l10r10-{big,mid}` and `/run/user/1000`).

## 1. Verdict

**The analyzer *request* is identical on both legs. The *execution envelope* is not — and for the
mid leg that difference is decisive: it is not in flight, it is dead.**

- **BIG leg — SEALED, id RE-DERIVED, envelope byte-identical.** `arc2-r10-big.service` ended
  `Result=success` / `ExecMainStatus=0` at 2026-10-18T21:20:23-03. Its stdout envelope is
  **byte-for-byte identical** to the r7 committed receipt (`cmp` → 0 differing bytes; both
  sha256 `a77ebee8794fb5951cc5bc79f46000e1fdd29c3ed09542d30c791a89941c218a`, 5204 B) and
  carries the same `evidence_id ev_a4aa9b0d…`. Rerun id-stability at the 91.6MB scale point is
  **confirmed, not inferred**: the r7 entry's last named unknown ("A second run was not made; id
  stability across a rerun is UNKNOWN", `corpus/knowledge/2026-10-18-arc2-r7-pe-wall.md:8`) closes
  on the *equal* branch. The id is insensitive to wall time (23m58.082s vs 23m44.663s, +13.4s),
  memory peak (7.8G vs 7.9G), swap peak (769.1M vs 53.1M), and host coexistence.
- **MID leg — NOT in flight; kernel-OOM-killed, no `evidence_id`.** `arc2-r10-mid.service` is
  `failed`, `Result=oom-kill`, `OOMKills=1`, `MemoryPeak=9663676416` == `MemoryMax` (9 GiB),
  `MemorySwapPeak=1073741824` == `MemorySwapMax` (1 GiB), 53.602s wall. REA reported it as
  `code: cancelled` / `retryable: true` with **zero `evidence_id`** — the r4 mislabel class the r8
  erratum names (`corpus/knowledge/2026-10-18-arc2-r7-pe-wall.md:44-45`). **No mid-rung id
  re-derivation exists.** The mid scale point stays UNKNOWN; this is named debt, not a result.
- **Where the rerun is not byte-identical (adversarial finding).** Params match, target bytes
  match, but the mid rerun carries a **9 GiB cgroup cap + 1 GiB swap cap that the r6 original never
  had** (r6 ran uncapped from a shell, `timeout -k 60 5400` backstop only, peak tree RSS 18.263 GiB
  — `corpus/knowledge/2026-10-18-arc2-r6-pe-midrung.md:44-50`). The mid leg is therefore
  **OOM-by-arithmetic, exactly as predicted** at `.ufo/waves/arc2-loop1-round6/CR10.md:14`
  ("Cgroup-OOM-by-arithmetic if round-4 decompile workers return"). It died 53s in, before any id
  could re-derive. Secondary envelope deltas: `TMPDIR` path on both legs (provably request-neutral —
  the digests match); launcher form (`npx -y rea-agents@6.5.0` vs r6's direct `node …/rea.mjs`, same
  npx cache `ad9a3fdbcad992c6`); `JAVA_HOME` now explicit on both (unknown for r6's mid run).

**Answer to the seat question:** yes for the request, no for the envelope. On the axis the id keys
(target content + analysis params) the rerun is identical — proven empirically, not by intent. On
the axis that determines whether the mid rung can hold (cgroup memory ceiling) the rerun is
materially different, and that is what killed it.
