## Verdict

**Holds, with a wording refinement.** The entry's "The saved pages list higher ids first" is true of every saved page measured. But the live API is *not* ordered by id: its default key is `created_at` descending (newest submission first), and id-descending follows only from id assignment at insert time. `ordering` is a real query parameter, yet `ordering=id` and `ordering=-id` are silently ignored; only `created_at` / `-created_at` change the result order.

## 4. Does the entry's wording hold?

- "The saved pages list higher ids first" — **holds** (26/26 multi-row pages strictly id-descending; 59/59 non-empty pages non-increasing by id).
- Mechanism refinement worth folding in: the order is *submission time* descending and id-descending follows from id assignment at insert; the API cannot be asked for id order, so a future snapshot may contain a page where a higher id follows a lower one (observed 3 times in 20 default pages of 100 rows). Suggested wording: "the saved pages list the newest submissions first; ids descend in every saved page because ids are assigned at insertion, and the server's ordering key is `created_at`, not `id`".
- The entry's rule "never take the first 4byte.directory result" is unaffected and now rests on a firmer reason: the first row is the newest submission, which for `transfer(address,uint256)` is the 2023 junk row `workMyDirefulOwner(uint256,uint256)`; the correct `transfer(address,uint256)` is the oldest row (id 145, 2016).
