# CR10 (critic) — 9G on a 6.9G floor: is THIS run an OOM-by-design?

Wave arc2-loop1-round6 · Seat CR10 · 2026-10-18T17:46–17:50-03 · read-only except this file · HEAD `54bc9dd`. Service `arc2-r6-pe` was not signalled. Custody not in scope (no 5/5 claim).

## Verdict

**THIS run is not an OOM, and it is not an OOM-by-design that fired.** `arc2-r6-pe` died `Result=exit-code` / status 1 in 7.554s at `MemoryPeak=2208227328` (2.06 GiB, 23% of the 9 GiB cap), swap peak 0. The kernel window has no OOM line. `user@1000.service` `oom_kill` is still 2 — the same count round 4 recorded. Cause is a pre-script abort: unknown analyzer `Decompiler Parallel Convention Analysis`. Analysis never started, so the cap was never tested.

**The slogan "9G on a host that showed a 6.9G floor" is a category error if it means the host only has 6.9G.** The 6.9G figure is round 4's *MemAvailable floor during coexistence* (6926 MiB @ 19:05:36Z), not RAM and not a process floor. This host's `MemTotal` is 30.25 GiB. At 17:46:26-03, `MemAvailable` was 15.0 GiB, which is above 9 GiB. Ancestor `memory.max` is `max`. A 9 GiB ceiling can bind as a contained kill on the host as measured now.

**The design is still a bad containment story, in two conditional senses — neither of which this invocation realized:**

1. **Host-safety fails if that floor returns.** 9 GiB exceeds 6.76 GiB by 2.24 GiB. `MemoryMax` is a ceiling, not a reservation. On a host with only 6.76 GiB available, the unit can exhaust `MemAvailable` before hitting its own cap. That is the trade-off SC1 already named for any cap above 7G. `MemoryHigh=infinity` means no throttle before the hard limit.
2. **Cgroup-OOM-by-arithmetic if round-4 decompile workers return.** Round 4 was already 7.0 GiB at 4m42s and climbing at 307 MiB/s; +2 GiB of cap is ~6.7s of that slope. `-Xmx6G` did not bind then (java 3.20 GiB + 10 `decompile` children 3.60 GiB). 6G heap + 3.60G workers = 9.6G > 9G `MemoryMax`. The planned shrink (disabled analyzers + worker reduction, `SCORECARD.md:899-900`) did not engage: the unit has no worker knob, and the analyzer script validates every name before disabling any, then threw on the third name. Zero analyzers were turned off.

Do not file this terminal state as `oom-kill` or as containment that survived the wall. The wall was not reached. C1's big leg is a typed failure, but the cause string is analyzer-name abort, not OOM.
