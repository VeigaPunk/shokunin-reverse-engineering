### 2.2 The two unit types, from the installed man pages

`systemctl --version` → `systemd 261 (261.2-1-arch)`. Pages:
`/usr/share/man/man1/systemd-run.1.gz`,
`/usr/share/man/man5/systemd.scope.5.gz`,
`/usr/share/man/man5/logind.conf.5.gz`.

**Observation** (`man systemd-run` DESCRIPTION). A transient service
"will run in a clean and detached execution environment, with the
service manager as its parent process"; `systemd-run` "start[s] the
service asynchronously in the background and return[s] after the
command has begun execution" unless `--wait` / `--pipe` / `--pty`. A
`--scope` command "will be executed by systemd-run itself as parent
process and will thus inherit the execution environment of the caller";
"Execution in this case is synchronous, and will return only when the
command finishes."

**Observation** (`man systemd.scope` DESCRIPTION). Scope processes
"generally remain children of the original process that forked them
off"; that process collects their exit statuses. Scope lifecycle is
bound to "the existence of at least one process in the scope", not to
one main PID.

**Observation** (`man logind.conf` `KillUserProcesses=`). If true, "the
scope unit corresponding to the session and all processes inside that
scope will be terminated." User-manager processes (`user@.service`)
"may allow users to run processes independent of their login sessions"
depending on linger. `KillUserProcesses=yes` "will break tools like
screen(1) and tmux(1), unless they are moved out of the session scope."

**Observation** (this host, 21:13Z). Effective
`KillUserProcesses` is false (`busctl get-property org.freedesktop.login1
/org/freedesktop/login1 org.freedesktop.login1.Manager KillUserProcesses`
→ `b false`; distro file has the setting commented `#KillUserProcesses=no`).
`loginctl show-user vgpnk -p Linger` → `Linger=yes`. User manager pid
1539, PPID 1, started `Sat Oct 17 00:00:07 2026`
(`/usr/lib/systemd/systemd --user`).

**Inference.** On a host with `KillUserProcesses=yes`, a `--scope` run
that stays inside the caller's session dies at logout; a user service
can outlive that logout only while the user manager stays up
(`Linger=yes`). That logout form is **not armed here**. The coupling
that is armed regardless of that setting: `--scope` blocks in a process
that is a descendant of the dispatcher, and the workload remains a
child of the forking process. Killing that process tree stops the
scope. A transient service's parent is the user manager, which this
wave does not own.

**Unknown.** This seat did not kill a caller to test survival. Do not
upgrade the man-page mechanism to "proven on this host by a kill test."

## The mechanism (installed man pages, systemd 261.2-1-arch)

**Observation.** `man systemd-run`: a transient service runs detached,
with the service manager as its parent, and `systemd-run` returns after
the command has begun. A `--scope` command is executed by `systemd-run`
itself as parent, inherits the caller's environment, and `systemd-run`
does not return until the command finishes. `man systemd.scope`: those
processes generally remain children of the process that forked them.
`man logind.conf` `KillUserProcesses=`: if true, logout terminates the
session scope and every process inside it; processes under the user
manager can outlive login sessions when lingering is enabled.
`KillUserProcesses=yes` breaks `screen`/`tmux` unless they are moved out
of the session scope.

**Observation, this host.** Effective `KillUserProcesses` is false
(`busctl` property `b false`). `Linger=yes`. The logout-kill form is
not armed here. Record both settings; do not copy another host's.

**Inference.** The coupling that does not depend on that setting: a
`--scope` workload is a descendant of the dispatcher, and the dispatcher
blocks in `systemd-run` until the command ends. An agent that tears down
its process tree stops the scope. A named transient user service is
parented by the user manager. Prefer that form when the run must outlive
the dispatching turn. **Unknown:** survival past an actual caller kill
was not tested on this host. Do not write "proven" for that sentence.

## Standing rules (parent process)

1. **Long run, short dispatcher → transient user service, not `--scope`.**
   `systemd-run --user --unit=NAME` (no `--scope`), with `MemoryMax` /
   `MemorySwapMax`, a disk `TMPDIR`, and `--property=Type=exec` when a
   failed exec must fail the start. `Type=simple` reports start success
   at `fork`, before `execve` (`man systemd-run`); that caveat is from
   the man page, not from the round-6 exit (that exit was recorded).
2. **Do not explain a unit death as caller-teardown unless the caller
   exited first.** Require a `Stopping`/`Killing` line, or a dead
   launcher, before the unit's result. An `exit.txt` written by the
   launcher after `systemd-run` returns is evidence the caller was alive.
   Round 4 is the counterexample: memcg OOM, launcher still writing.
3. **Record `KillUserProcesses` and `Linger` with the recipe.** Service
   mode outlives logout only while the user manager stays up. On this
   host linger is on and session-kill is off; a host with the opposite
   pair needs both the service form and linger, or the "independent"
   unit dies at logout anyway.
4. **Service mode is not a result.** It does not raise the memory cap,
   does not validate analyzer names, and does not seal an evidence id.
   Round 6 exited in 7.554s on `execution_failure` with the cap untouched.
   Judge the analysis on the envelope, not on the unit type.
5. **Failed transient units stay loaded** when `CollectMode=inactive`.
   `systemctl --user reset-failed NAME.service` is still the residue
   step (`CR4.md:272-274` for the scope class). Do not cite a post-reset
   `Result=success` as the run's result.
6. **A fictional cause is worse than a real one.** Recording "died with
   the caller" for an OOM (a) invents a defect, (b) hides the memory
   wall, and (c) sends the next retry after the wrong knob. Same class
   as the dispatch-count lesson: when the journal and the note disagree,
   believe the journal.
