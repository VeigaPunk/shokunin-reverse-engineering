# C1DevArmB — R50-C1 dev arm, carriers c6490 + c6430 (pre-freeze, scratch only)

**Verdict: both carriers extract cleanly through REA 6.5.0 and are fit for the freeze, but the plan draft names the wrong member path and wrong sizes for them. Fix those two before the freeze.** Each carrier gives `squashfs_v4_le`, one chunk, `extraction_failed false`, and published files equal to the oracle (0 missing, 0 extra, 0 sha256/size diffs). The c6430 rerun projection was stable over three runs under the round-41 `projection()` (all four profiles). Nothing was committed; no vendor bytes are in the lane tree.

## Risks / not run

- Not run: the `c1-counter` port, evidence-id recomputation, `--carrier-cache` rerun path (no instrument exists yet); the oracle arm's `sasquatch` cross-check (the plan has no `-be` producer for LE; I used `unsquashfs` 4.7.5 + `sqfs-list.py`).
- The BE `sqsh` ARM member of these two boxes (`./var/remote/var/tmp/filesystem.image`, 5.4 / 6.0 MB) is a different carrier (round-41 handler); not touched.
- An unprivileged `unsquashfs` run exits 2 because of `dev/led`; a data-run oracle script must treat exit 2 with exactly that message as expected (or pass `-no-exit-code` style via `sqfs-list.py` only).
- `sasquatch` is 4.5.1 in `~/.local/bin`; the unblob `squashfs_v4_le` handler uses it. A host with a different `sasquatch` is the counter-time risk (F8 shows exit 0 with a missing extractor), so the counter must read the gap/file clauses, not exit codes.
- No tools installed or changed; no pacman. Network: two `curl` downloads (35.9 and 39.7 MB) into scratch only; the scratch is deleted after this report.
