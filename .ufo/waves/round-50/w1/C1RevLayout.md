# R50-C1 wave-1 seat `C1RevLayout` — little-endian AVM layout, reverse-engineered on real members

Base `7c678ae6d97aedb969fd253b52b3d2882ef1e186`. Measured 2026-10-28 (UTC 23:31-23:43). Seat dir `.ufo/waves/round-50/w1/C1RevLayout/` (receipts, probe tools, logs; no vendor bytes). Scratch removed after copy.

## Verdict

1. **No byte-level property marks the LE AVM layout as a layout.** Both little-endian members decode, field by field, as a stock `mksquashfs` 4.x LE image: LE superblock, LE metadata headers (exact walk), inode types of the stock family, xz data blocks at 65536 with 8192-byte metadata dictionaries, flags `0x2c0` = stock `-no-xattrs`. A byte-order-mixed reading (the AVM-BE pattern) is refuted: reading the LE members' superblock as BE gives nonsense (`bytes_used` ≈ 1.3e17).
2. **The only AVM-specific bytes on the LE members are two packaging facts**: (a) the header marker `mkfs_time == bytes_used`, and (b) an **8-byte footer** after the 4 KiB zero pad (`23 de 53 c4` + 4 bytes). (b) is not a squashfs field; it is also present on the AVM-BE member `c6430 ./var/remote/var/tmp/filesystem.image` (one BE sample), so it marks AVM packaging, not the LE layout. Its last 4 bytes match no CRC32 / CRC32~ / Adler-32 / CRC32C over `[:bytes_used]`, `[:aligned]`, `[:-8]`, `[:-4]` (LE and BE readings); not identified.
3. **(a) is forgeable with stock tools.** `mksquashfs … -no-xattrs -mkfs-time <bytes_used>` (two passes; `bytes_used` is fixed by content) gives a stock LE image with `mkfs_time == bytes_used` and flags `0x2c0`, indistinguishable at every superblock clause of the plan's predicate. The marker cannot establish AVM provenance.
4. **The LE extraction path never reads the marker.** unblob 26.6.4 `handlers/filesystem/squashfs.py` tests `is_avm` only inside the `Endian.BIG` branch; the LE branch appends `-le` to `sasquatch` unconditionally (measured: `sasquatch -le -no-exit-code -f -d` exit 0 on a7530).
5. **Plan defects found (fold before freeze):** (i) the **c6430 carrier chain is wrong** (member path absent; see F1); (ii) `sqfs-list.py --layout avm` **refuses** `hsqs` (exit 2 by design), so the counter's layout clause must use `--layout le`; (iii) on c6430-x86 the member contains a char device `dev/led`: `sasquatch` and `unsquashfs` without `-no-exit-code` exit 2 as non-root, so any counter-time rerun must use `-no-exit-code` (the unblob call does); (iv) a whole-member carrier (34 005 000 B) yields an **UNKNOWN 8-byte chunk** in unblob — the carrier definition (whole member vs carved to `bytes_used`) must be pinned explicitly.

## Byte-level answer to the assignment's question

**Is there any byte-level property other than `mkfs_time == bytes_used` that marks the LE AVM layout?** No property marks the *layout*. Two byte-level properties separate the genuine members from a stock image, and neither is in the LE structure: the 8-byte footer after the 4 KiB pad (observed on 3/3 AVM members, 0/2 controls, unidentified value) and the `NO_XATTRS` flag (a stock option, not a mark). `mkfs_time == bytes_used` is itself a stock-settable header value (F9).

## Sentence the entry may safely state (draft for L1)

> Genuine FRITZ!OS little-endian members (`hsqs`, v4.0, xz, block 65 536) carry the AVM header marker `mkfs_time == bytes_used` and an 8-byte footer after the 4 KiB pad. Apart from those two packaging facts, their superblock, metadata-header, inode and table structures decode as a stock little-endian SquashFS 4 image (the same flags, block size and xz dictionary rule as `mksquashfs -comp xz -b 65536 -no-xattrs`). The marker is a header value any stock writer can set, so it is not evidence of AVM provenance; the footer's last four bytes are not identified. unblob 26.6.4's `squashfs_v4_le` path does not read the marker; it runs `sasquatch -le`. ## Limits

- Two LE members (a7530 ARM/IPQ4018 per plan; c6430-x86) and one BE member. Not the full set of "dozens" the L1 probe reported; the L1's `c6430` row was evidently taken from a different member than `./var/tmp/`.
- The footer's last four bytes were not identified (no CRC/Adler/CRC32C match; no signature check run). A signature over the image is possible (`./var/signature`, 128 B in the a7530 tar) and was not tested.
- Stock comparison is one `mksquashfs 4.7.5` build over 600 Python sources and a 7-file tree; the AVM build's squashfs-tools version is not known. The claim "stock-shaped" rests on fields and counts, not on byte-identity with any stock build.
- `sasquatch` 4.5.1 and `unsquashfs` 4.7.5 agree on a7530; c6430-x86 was compared only with sasquatch (`-no-exit-code`), since unsquashfs stopped at the device.
- No REA run here (see above).
