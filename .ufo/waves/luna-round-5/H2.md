## CLAIM
H2 audit of byte/MB/MiB/GB notation and conversions in both assigned round-4 knowledge files; no source/runtime verification claimed.

## METHOD
Read both complete files and swept unit-marked lines: `corpus/knowledge/2026-10-13-r4u-01-firmware-deep.md:1-119` and `corpus/knowledge/2026-10-13-r4-12-godot-arm64-scale.md:1-154`. Recomputed hex and byte conversions with Python (`B/10^6` for MB; `B/2^20` for MiB). Output: `0x1c01dc8 = 29367752 B`; `0x505b000 = 84258816 B`; `91662336 B = 91.662336 MB / 87.416016 MiB`; `69538816 B = 69.538816 MB / 66.317383 MiB`; `128 MiB = 134217728 B`; `13756760 B = 13.756760 MB`; `(0xbc0000-0x400000) B = 7.75 MiB`.

## FINDINGS
- **r4u-01:** Decimal `MB` is used; `MiB` is binary (lines 3, 37, 47, 71-73, 112). Whole-MB `~29/84 MB` agrees with listed blob sizes at lines 12-13. Two conversions at line 41 are wrong: `0x1c01dc8` is 29,367,752 B, not 29,358,536 B (−9,216); `0x505b000` is 84,258,816 B, not 84,242,432 B (−16,384). The first correct value agrees with the embedded extent at line 49 (29,367,752 B ≈29.37 MB). `13.7 MB` at line 65 truncates 13.756760 MB; nearest-tenth rounding is 13.8 MB. The `~8 MiB` span at lines 71-73 is 7.75 MiB, acceptable as a whole-unit approximation.
- **Godot:** Decimal MB and binary MiB are distinguished (lines 19, 26); `.text` conversions are right. 91,662,336 B is 91.662336 MB / 87.416016 MiB, so repeated `91.6 MB` (lines 8, 35, 117, 136) is truncation; conventional nearest-tenth is 91.7 MB. The 128 MiB cap is binary and correctly exceeds the file size. `2.36/1.95 GB` RSS and `30 GB` RAM (lines 77, 131) lack source byte counts; `6–8 G` (lines 93, 150) does not specify GB vs GiB, so those conversions are unverifiable.
