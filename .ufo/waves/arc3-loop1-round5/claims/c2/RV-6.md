## Corrections to hand to the parent (append-only; no edits made here)

1. **r1 mixed text-file/decoded-byte units — CORRECTED needed.** In `2026-10-19-arc3-r1-evm-real-solc.md:12`, `Rv2Token.creation.hex` has a 3,942-byte text carrier and SHA-256 prefix `e6517fb7`; decoded initcode is 1,971 bytes and has SHA-256 `04e07f54`. The appended correction at :31 calls the `.hex` file “1,971 B”, so the two lines use different units for the same path. State both explicitly. Likewise `Smoke_sol_Smoke.bin` at :15 is 1,370 bytes of hex text, SHA-256 `530efc7b`; decoded initcode is 685 bytes, SHA-256 `08299f31`. The current line combines the decoded length with the text-file digest. Suggested fix: distinguish text carrier size/digest from decoded bytecode size/digest in an append-only erratum.
2. **r3 CBOR bytes are not executable PUSH4 immediates — CORRECTED needed.** `2026-10-19-arc3-r3-evm-optimizer-shapes.md:26` says the noopt VaultB carries `43000825` as a non-dispatch PUSH4, and Rv2TokenOpt has seven PUSH4 immediates including that CBOR value. Direct disassembly of code regions gives VaultB nopt 15 PUSH4 sites, all selector sites (code end 3110); Rv2TokenOpt has 6 sites (5 selectors + panic, code end 925). `43000825` occurs only in the terminal CBOR trailers (offset 3157 and 972 respectively), not as a code-region PUSH4. VaultB opt200 has code end 1568 and its trailer token at 1615. Reword the “whole-file candidate” note to distinguish metadata byte patterns from EVM instructions, append-only.
3. **Core-status conflict — CORRECTED/adjudication needed.** Each corpus scope line explicitly says “RESULT-class, no Core promotion” (`r1:33`, `r3:35`, `r4:30`). However current `PROVINCE.md:92-93` labels the real solc carriers “Core, arc3-r1/r3”; the Vyper r4 carrier is named without Core. The no-Core disclaimer exists in corpus but is contradicted by the lane's current summary. Parent should reconcile status; this seat did not modify PROVINCE.
