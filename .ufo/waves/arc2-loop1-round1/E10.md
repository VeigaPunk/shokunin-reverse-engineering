## 3. Prefix-identity reasoning (what proves append-only, and what does not)

Append-only means: **the new file's bytes have the old file's complete byte
string as an exact prefix**. Verification primitives, all tested this session
on scratch files (`/tmp/arc2-l1r1-E10-cmp`) with GNU cmp 3.12:

- `cmp -n N old new` → exit 0 iff the first N bytes are identical; exit 1 on a
  difference within N or on EOF (new shorter than N). Negative controls: 1-byte
  rewrite at offset 0 → rc 1 (`differ: byte 1`); shorter file → rc 1
  (`cmp: EOF on 'b' after byte 5`).
- `git diff --numstat <old> -- <file>` → `A B` lines; the append-only gate is
  **B = 0** (insertions only). Blob hashes and commit hashes both work as
  `<old>` (tested: `git diff --numstat 0cb945bd… -- f` and
  `git diff --numstat 4b806e14 -- f` both → `25 0` after the E8 sim).
- `head -c 8568 "$F" | git hash-object --stdin` → must equal
  `0cb945bd0514f8b5e77710409ef7f98d33ced02a`.

**The trap (found in clone sim).** `cmp -n 8568 <(git show HEAD:$F) "$F"`
is meaningful only **before** the landing commit. After the commit, `HEAD:$F`
*is* the new bytes, so the command compares the new file's first 8568 bytes
against themselves — rc 0 trivially, proving nothing. Demonstrated in
`/tmp/arc2-l1r1-E10-clone`:

```text
pre-commit:  cmp -n 8568 <(git show HEAD:$F) "$F"  -> rc=0 (meaningful)
post-commit: same command                          -> rc=0 (VACUOUS)
post-commit: git diff --numstat HEAD -- "$F"       -> (empty; no signal)
post-commit: cmp -n 8568 <(git cat-file -p 0cb945bd…) "$F" -> rc=0 (DURABLE)
```

The P1-style two-sided form `cmp <(git show HEAD:$F) <(head -c 8568 "$F")`
does **not** silently pass post-commit — it fails loudly
(`cmp: EOF on '/dev/fd/62' after byte 8568`) — so it is safe but returns a
false negative once HEAD has moved; prefer the pinned-identity forms below.
