## Findings by severity

**M1 — the v2→installed source delta is unverifiable from retained artifacts (verification gap, disclosed).** The v2 bytes (`a7253d24…`) are retained nowhere — `repairs/disk/` holds only the three receipts; the prep report pins v2's digest/size only. Actionable only if the copy is ever cited as selftested; the L1 final run must be a fresh measured run of `e6121720…` with its own receipt.

**M2 — the docstring's "any other path-qualified command is RED" is false for one class; the only false-negative class is under-disclosed at registry/runtime level.** [static] The path alternative requires a leading `./`, `../`, `~/`, or `/` (`_COMMAND`, `disk-command-audit.py:45-48`), and the bare-name lookbehind `(?<![\w./])` excludes any `/`-preceded token. A relative multi-segment spelling without a recognized prefix — e.g. `bin/find /fast/scratch` or `usr/bin/du /fast/scratch` after a `cd` — matches **neither** alternative: no RED, no GREEN, no verdict at all, silently. That contradicts the docstring (`disk-command-audit.py:6-8`). The prep report discloses it precisely ("Path-form limitation", `prep/R33DiskGuard.md` Limitations; correction bullet "relative multi-segment paths not recognized") and WLesson summarizes it, but the tool's own runtime `LIMITATION scope` line (`LIMITATION_SCOPE`: cwd, variables, aliases, command substitution only) and the SKILL registry row/prose (`SKILL.md:1108`, `:1111`: adds only "shell functions") omit it. Practical risk is low — bare, `./`-prefixed and absolute forms are covered, and misses require an unusual PATH-relative spelling — but this is the single gap that can turn a prohibited command into zero output, so the registry row should carry it.

**L1 — exit-code precedence errors>red is undocumented.** [static] `run_files` returns 2 (`RESULT ERROR`) when any file errors, even if RED rows were found and printed, because `if errors:` precedes `if red:` (`disk-command-audit.py:147-152`). Defensible (an unevaluated file forbids an all-clear), and RED evidence survives on stdout, but neither the docstring exit map, `SKILL.md:1108`, nor the prep report states the precedence.

**L2 — GREEN is token-based, not command-position-based.** [static] Any textual `/usr/bin/find`/`/usr/bin/du` token followed by a scratch mention in the tail yields GREEN: `ls -l /usr/bin/find /fast/scratch` or `FOO=/usr/bin/find /fast/scratch` each produce a GREEN `absolute-*` row though no find/du is invoked. GREEN never affects exit status and "GREEN lines do not prove execution" is printed, but the narrower cause (no command-position parsing) is disclosed only in the prep report ("Command-position limitation"; correction "command-position parsing incomplete"), not at runtime/registry level.

**L3 — `_BREAK` omits single `&`, `(`, `)`, `$(`, `<(`.** [static] `_simple_tail` (`:49`, `:78-81`) stops only at `&&`, `||`, `;`, `|`, backtick, so tails bleed across same-line constructs (`du . & ls /fast/scratch` flags `du`; `du . >(cat /fast/scratch/x)` flags `du`). Tail bleed can only *add* scratch mentions, never remove them, and GREEN does not consult the tail — so this direction produces RED false positives only (safe direction), consistent with the printed "RED hits can be false positives". The `cd /fast/scratch && find .` cwd case is correctly isolated by the `&&` boundary and disclosed as unhandled.

**L4 — minor disclosure imprecision.** `SKILL.md:1108`'s "14 lexical and 3 outer-CLI fixtures" attaches "fixtures" to both groups; the 14 are in-memory `audit_text` cases, only the 3 outer cases use fixture files (prep Limitations states this precisely). `SUMMARY lines=` counts logical continuation-joined lines, not physical — the prep receipt's "159 logical lines" phrasing is the accurate one, the SKILL row is silent.
