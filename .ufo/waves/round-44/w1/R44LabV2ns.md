## Independence analysis

An oracle is admissible only if its producer differs from the tool under test (the draft's own
wording: `unsquashfs` is independent because it is "a different producer than sasquatch").
Every reader that can open `zlqs`-magic v2 images is a squashfs-tools-4.3-patchset descendant
(sasquatch) or the unblob expected tree generated by it. Independent implementations tested —
kernel-reference squashfs-tools 4.7.5 (`unsquashfs`, `sqfscat`), 7-Zip's separate squashfs
parser, backhand's independent Rust reimplementation, PySquashfsImage's independent Python
reimplementation, and binwalk's signature scanner — all refuse on the nonstandard magic or lack
a v1/v2 profile entirely. No feasible patch-magic workaround exists inside claim scope:
rewriting `zlqs`→`sqlz`/`hsqs` would still need a v2 reader willing to accept it, and a mutated
carrier is no longer the frozen fixture bytes.

## Boundary note (why this matters)

sasquatch -ll DOES produce the full member tree (`apple1–apple4.txt`), so the fixture is valid
and the handler works — the blocker is purely oracle independence, not image validity. If a
future round finds an independent reader (e.g. a v1/v2-capable backhand release, or a kernel
mount test), v2ns becomes promotable with the same two-oracle pattern used for v1/v2.
