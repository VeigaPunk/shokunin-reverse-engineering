### Two normalizer traps found in the sibling artifacts (measured, not asserted)

1. **`__default__` is not a selector-bearing function.** Both EX-02's and EX-03's
   `method_identifiers` outputs list `__default__(): 0x89402a72`; the recovered set
   excludes it. Checked at byte level: `89402a72` does not occur in either runtime's
   bytes at all (not as an immediate, not as data). Vyper dispatches its fallback by
   fallthrough, so the correct K is "method_identifiers minus `__default__`".
2. **Vyper's `method_identifiers` drops leading zeros in the hex string.** EX-03's
   file carries `0x95ea7b3`, `0xc751377`, `0x6fdde03` (7 chars) for
   `approve`, `fee_of`, `name`. A raw set comparison against the probe's `0x095ea7b3`
   style reports three spurious "missing" selectors. Left-padding to 8 chars makes the
   set comparison MATCH exactly (22/22).

## 4. Vyper dispatch shape — reconstructed at byte level (the round's new class)

Prologue is `5f3560e01c` (PUSH0 CALLDATALOAD PUSH1 0xe0 SHR) — the same class the r3
entry measured for solc, **not** the `366000…` class. The dispatcher differs:

```
5f 35 60 e0 1c        PUSH0 CALLDATALOAD PUSH1 0xe0 SHR
60 02 60 0d 82 06     PUSH1 0x02 PUSH1 0x0d DUP3 MOD      ; slot = selector % 13
60 01 1b              PUSH1 0x01 SHL
61 06 00 01           PUSH2 0x0600 ADD                   ; table base
60 1e 39              PUSH1 0x1e CODECOPY                 ; 13 x uint16
5f 51 56              PUSH0 MLOAD JUMP
```

Then per selector:

```
5b 63<sel> 81 18 61<next> 57   JUMPDEST PUSH4<sel> DUP2 XOR PUSH2<next> JUMPI
<12-byte body>
```

- Table at offset `0x600`: `0x29c 0x5e7 0x50b 0x400 0x5ac 0x43f 0x53d 0x5e7 0x590 0x574 0x382 0x5e7 0x18`
  — every entry is a JUMPDEST.
- 15 entries reachable by walking the chains from the 11 distinct heads; exactly the
  15 planted selectors.
- **Probe `bytecode_offset` semantics on this class:** every reported offset equals
  `entry_jumpdest + 12` — the first byte *after* the match test, i.e. the fall-through
  body entry. Verified for all 15: `probe_offset - push4_immediate_offset = +11`
  uniformly, and `code[offset-1] == 0x57` (JUMPI) for all 15. **No probe offset lands
  on a JUMPDEST** (0/15), unlike the solc carriers in r1/r3 where every offset was a
  JUMPDEST. This is a distinct offset-semantics class and a candidate erratum for the
  "offsets land on JUMPDEST" reading, which is therefore scoped to solc-convention
  carriers.

## 5. Inference quality — a measured degradation on this carrier

`inferred_state_mutability` agrees with the compiled ABI on only 7/15 `CarrierV`
functions; the 8 disagreements are all "probe says `payable`, ABI says view/pure/nonpayable":

- `is_owner`, `balances`, `balance_of` → ABI `view`, probe `payable`, and probe
  `inferred_arguments` reads `uint256` where the ABI declares `address`.
- `fee_of` → ABI `pure`, probe `payable`.
- `set_fee`, `withdraw`, `fee_quote`, `fee_on` → ABI `view`/`nonpayable`, probe `payable`.

Root cause is visible in the bytes: the vyper dispatcher's match test does not
pre-check `CALLVALUE`, and each *non-payable* body starts with `CALLVALUE PUSH2 0x5fc
JUMPI` (the revert guard) — so the value check lives in the body, not the dispatch
test. Where solc's linear/binary dispatchers put the mutability signal in the dispatch
tree, vyper's does not, and the upstream inference falls back to `payable`. Selector
recovery is unaffected (15/15); only the mutability/argument inference degrades.
This is an honest measurement of the tool's limits on a new dispatch class, not a
recovery failure.

## 6. Envelope deltas and input traps (measured)

- **6.4.0 vs 6.7.0:** 6.7.0 adds a top-level `relationship_coverage` key (value
  `null` here); all other keys and all payload content identical. `raw_result.metadata`
  is `null` on this carrier under both pins (r1/r3 solc carriers reported CBOR trailer
  metadata) — the terminal CBOR trailer is present in the bytes but not decoded here.
- `--full-output` wraps the envelope as `{ok, data, meta}`; `data` is byte-equal to
  the bare `--format json` envelope (`meta` = `{"command": …, "duration": "134ms"}`).
- Default (no `--format json`) emits the same content in TOON form.
- **Trap — `hex` declared on a `.bin` carrier:** exit 1, typed
  `{"code":"invalid_request","category":"invalid_input", …}` with
  `issues[0].reason == "invalid_format"` ("Hex carrier must be valid UTF-8").
  Fail-closed, no silent success.
- **Trap — `raw` declared on a `.hex` carrier:** exit 0, 0 functions, and the decoded
  `bytecode.sha256` equals the hex *file's* own sha256 (`e0b1021c…`) — i.e. the ASCII
  text is decoded as code. Same class as r1's `ev_60062ad0…` and r3's `ev_704ce585…`.
  Parsed-and-empty, not an error.
- **Creation blob** (`CarrierV` creation.hex, 1,637 B): n=0, decoded `3c667396…` —
  parsed-and-empty, consistent with the r1 erratum that creation blobs *do* embed the
  runtime dispatch table but the tool's scope is the runtime entry point.
- **Id domain, re-measured:** same bytes + same request at the same path re-derive the
  id (rerun ≡ first run). Same bytes at a different absolute path mint a different id
  (`ev_d1792f57…` at my scratch path vs EX-04's `ev_405e2a2a…` at theirs). Format-shape
  variants (uppercase / `0x` prefix) also mint fresh ids while decoding to the same
  bytecode sha256. Compare by decoded `bytecode.sha256` + function payload, never by id.
