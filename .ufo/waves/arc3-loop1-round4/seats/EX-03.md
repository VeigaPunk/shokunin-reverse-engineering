## 2. Proposed changes

**none** — no patch text from this seat. Chain notes for the entry author:

- The correct ABI-derived K for a Vyper carrier is its **function** entries only;
  `method_identifiers` is not a drop-in K source (§4 trap 2).
- The `5f3560e01c` prologue is **shared** between Vyper 0.4.3 and the solc-0.8.37
  carriers the r3 entry measured — the anchor does not separate the compilers.
- Vyper's CBOR metadata sits in the **creation** blob, not the runtime (§4 attack 5) —
  the r1/r3 "creation blobs embed their runtime dispatch tables" reading is compatible
  with this, but the metadata placement is a new, separate fact.
- Probe `bytecode_offset` on this class equals the chain **body** offset (not a
  JUMPDEST) — measured by EX-06; a candidate erratum for the "offsets land on JUMPDEST"
  reading, which should be scoped to solc-convention carriers.

## 4. Attacks / refutations attempted (verdicts)

| # | attack | verdict |
|---|---|---|
| 1 | compile is nondeterministic | **refuted** — 3 independent runs; `runtime.hex` and `abi.json` byte-identical each time and equal to the landed artifacts |
| 2 | the local keccak is wrong | **refuted** — 3 independent implementations (pure-Python, `js-sha3@0.8.0` from the receipted r1 prefix, `node:crypto`/OpenSSL `keccak-256`) agree on all 22 signatures; Ethereum's own self-test vectors pass |
| 3 | the dispatch model is overfitted to one carrier | **refuted** — decoder generalizes unchanged to `CarrierV.vy`: N=13, 15/15, `sel % 13` holds 15/15 |
| 4 | every `PUSH4` constant is a selector | **refuted** — boundary-blind scan: 27 distinct constants, 5 false positives. Disassembly-aware (PUSH immediates skipped): 24 distinct, 22 real. `0x08c379a0` is the genuine `Error(string)` selector; `0xc4a11628` is not an instruction-boundary constant at all — it is the middle of the `Transfer` topic `ddf252ad…f5a4df523b3ef` inside a `PUSH32` |
| 5 | Vyper carries a solc-style CBOR trailer in the runtime | **refuted** — `--no-bytecode-metadata` leaves the runtime **byte-identical** (3337 B both ways) and shortens only the creation blob by 55 B; the trailer `…a1657679706572830004030037` carries the "vyper" marker and no `a1657679706572` appears in the runtime |
| 6 | the seat-line requirement is met by one lucky function | **measured** — 22 functions across 4 mutability classes; payable/view/pure separation is exercised |
| 7 | `method_identifiers` is a valid K source | **refuted, two ways** — (a) it strips leading zeros: `0x6fdde03`, `0x95ea7b3`, `0xc751377` are 7 hex digits, so a string compare silently misses 3 of 23; reproduces on `CarrierV.vy` (2 of 16). (b) it lists `__default__()` = `0x89402a72`, a correct keccak of that literal but a constant that occurs **0 times** in the runtime *and* **0 times** in the creation blob; the ABI instead carries `{"type":"fallback"}` with no selector, so set sizes disagree (23 vs 22). Taking `method_identifiers` as K injects one guaranteed false positive per contract |
| 8 | the prologue anchor separates Vyper from solc | **refuted** — Vyper's runtime opens `5f3560e01c600260168206…`, i.e. the same `5f3560e01c` class the r3 entry recorded as the solc-0.8.37 anchor. (A `case`-based check of mine first returned a false "NO" because the file carries a `0x` prefix — recorded so the false alarm cannot creep into the round.) |
