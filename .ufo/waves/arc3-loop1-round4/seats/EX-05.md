## 2. Proposed changes

**None.** No patch text. This seat's artifact is an input to the C1 claim (the
planted set the probe is measured against) and to the round's entry/records; it
makes no corpus/README/PROVINCE proposal of its own. Candidate one-liners for
the entry's observation list (parent's call, not a patch here):

- the Vyper 0.4.3 dispatcher on these carriers is the **sparse jumptable** path:
  `PUSH0 CALLDATALOAD PUSH1 0xE0 SHR` (`5f3560e01c`), then
  `PUSH1 0x02 PUSH1 <n_buckets> DUP3 MOD PUSH1 0x01 SHL PUSH2 <table> ADD PUSH1 0x1E
  CODECOPY` — a `method_id % n_buckets` bucket jump followed by **linear `EQ`
  compares within the bucket** (`PUSH4 <sel> DUP2 XOR PUSH2 <dest> JUMPI` per
  selector; `EX-04/out/opcodes.txt`). CarrierV: `n_buckets=0x0d` (raw head
  `5f3560e01c6002600d820660011b61060001601e395f51565b63d0e30db0…`); EX-02's
  smoke carrier: `n_buckets=0x03` (raw head
  `5f3560e01c60026003820660011b6100a201601e395f51565b63d09de08a…`). Both
  immediates are **predicted by Vyper's own codegen**: running
  `jumptable_utils.generate_sparse_jumptable_buckets` (from the venv, read-only)
  on the ABI signature sets yields n_buckets 13 and 3 respectively, with bucket
  sizes [1,1,1,1,1,1,2,2,2,3] and [2,2]. The path is selected in
  `codegen/module.py` (`_opt_codesize()` + `len > 4` → dense; else sparse) — so
  this is the **sparse** class, distinct from both the r1 `60003560e01c`-linear
  family and the r3 `5f3560e01c`-with-`GT`/`EQ`-binary-search-tree family the r3
  entry scopes. The entry's dispatch-shape claims should be scoped accordingly
  (measurement, not a patch: no entry file was touched by this seat);
- **Vyper's `method_identifiers` emits the 4-byte selector with leading zeros
  stripped** (`0xc751377`, `0x776076f`), so a naive string comparison against
  ABI-derived selectors reports two false mismatches on this carrier; consumers
  must zfill-8 (documented with both outputs in
  `planted-vs-method-identifiers.txt`).

   element types, dropped/added args, aliases like `setFee`/`totalDeposits`).
   Verdict: **0 collisions** — distinct canonical strings hash apart; the set is
   not vulnerable to the plausible spelling slips (`attacks.txt`).

   found a real defect in my own tool*. First run: `K=0`, rc=0, a silent empty
   artifact — a costume the freeze's honest-stop rules forbid. **Fixed**:
   `planted-vyper.js` now writes a typed header line (`typed result: EMPTY — the
   ABI carries zero function entries; no selectors exist to plant`), prints
   `typed result: EMPTY`, and exits 3. Re-run: rc=3, typed EMPTY on both inputs.
   Verdict: **refuted and repaired**, then all artifacts re-derived after the
   revision (manifest re-generated).
3. **Tuple canonicalization** (`f((uint256,address))` via `components`).
   Verdict: selector `31e3e7da` = the reference keccak of
   `f((uint256,address))` — canonicalization correct on a shape the carrier
   does not contain.
4. **ABI entry-order shuffle** (reversed array). Verdict: sorted sets identical —
   output is order-independent by construction.
5. **Duplicate ABI entry** (same function twice). Verdict: rc=0 with
   `duplicate_selectors: ["0xd0e30db0"]` surfaced in `planted-full.json` — a
   duplicate cannot hide silently.
6. **Self-check on the probe cross-check itself.** The `probe-pins/` copies were
   `cmp`-verified byte-identical to RV-2's originals, and the comparison reads
   selectors from the envelopes' `normalized_result.functions`, not from my
   notes. Verdict: pass.
7. **Peer-oracle inversion.** EX-09 used my `keccak_ref.py` as one of its two
   implementations; re-deriving their set with js-sha3 + node:crypto (neither
   used by them) tests my tool rather than restating it. Verdict: 7/7, full
   digests — my implementation is externally validated.
8. **Leading-zero normalization trap.** Comparing Vyper's `method_identifiers`
   raw against ABI-derived selectors yields 2 spurious mismatches. Verdict:
   **trap confirmed** (`0c751377` vs `c751377`, `0776076f` vs `776076f`);
   documented with both comparison outputs as a citation hazard for the entry.
9. **Dispatcher-shape self-refutation.** My first draft described the Vyper
   dispatcher as a "hash-based jump table / `PUSH4`-in-table lookup" from
   disassembly alone. Verdict: **refuted and corrected.** Reading the venv's
   vyper source (`codegen/module.py`, `codegen/jumptable_utils.py`) shows the
   carriers take the *sparse* path (`method_id % n_buckets` bucket jump, then
   per-bucket linear `EQ` compares), and running vyper's own
   `generate_sparse_jumptable_buckets` on both signature sets predicts the
   immediates observed in the bytes exactly (13 for CarrierV, 3 for Smoke) —
   `dispatch-shape.txt`. The report now states the source-checked version, and
   the correction is recorded here rather than silently applied.
