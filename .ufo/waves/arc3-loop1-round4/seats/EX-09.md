lands; each is backed by a sealed envelope named in `probe/`):

1. **Vyper runtime leg closes the named Unknown.** `inspect-evm-interface`
   recovers a Vyper-compiled carrier's selectors **K/K (7/7, zero missing,
   zero extra)** on five legs — hex and raw at both pins, plus the
   `0x`-prefixed form. Decoded `bytecode.sha256 54b14e30…` on every leg.
   Second independent Vyper carrier (EX-02's `Smoke`): **4/4** on four legs,
   decoded `415e6b1b…`.
2. **Third dispatcher prologue class, first hash-bucket table.** Vyper 0.4.3
   emits `5f3560e01c` (same prologue as the r3 solc class) but dispatches by
   `PUSH1 0x02 PUSH1 <n> DUP3 MOD PUSH1 0x01 SHL PUSH2 <table> ADD PUSH1 0x1e
   CODECOPY PUSH0 MLOAD JUMP` — an `n`-entry 2-byte **jump table** (n=6 here,
   n=3 for `Smoke`), whose targets are bucket heads, each head a
   `PUSH4 <sel> DUP2 XOR PUSH2 <next> JUMPI` chain. The bucket count `n` is
   carried in the prologue as the `MOD` modulus.
3. **`bytecode_offset` semantics are tool-relative, not JUMPDEST-relative.**
   On both Vyper carriers every reported offset equals **`PUSH4_opcode_pc + 11`**
   — the fall-through body entry after the 11-byte compare node
   (`63 sel 81 18 61 next 57`) — and **no** reported offset is a `0x5b`
   JUMPDEST. Contrast: on the r3 solc carrier `VaultB.opt200` all 13 offsets
   *are* JUMPDESTs. This is the second carrier class where the r3 entry's
   "offsets land on JUMPDEST" reading does **not** hold (carrier-A control was
   the first). The r3 line should be re-scoped to solc-convention carriers.
4. **`inferred_state_mutability` collapses to a binary** (`payable` vs the
   non-mutating string). On Vyper it reads `payable` for **every** function that
   takes an argument, whatever the ABI says. Refuted on an authored carrier:
   of 6 arg-taking functions spanning ABI `view`/`pure`/`nonpayable`/`payable`,
   **6/6** were reported `payable` while only **1/6** is payable in the ABI.
   The r3 entry's "upstream inference separates mutating from non-mutating, not
   pure from view" is the weaker form of this; the measured rule is stronger —
   *arg-taking ⇒ `payable`*, at least for this carrier family. `inferred_arguments`
   is likewise **arity-only**: every type is rendered `uint256`, including
   `address`/`bool` parameters (`args-field-census.txt`).
5. **Creation/initcode is typed parsed-empty, and the tool does not
   dispatch-scan inside an embedded runtime.** Vyper creation bytecode: 0
   functions, exit 0, `discovery_completeness: "unknown"`, on five legs — the
   same class as the solc creation control re-run here (0 functions,
   `ac614a6e…`). The Vyper initcode is a **superset** of its runtime (659 B =
   24 B prologue + the 581 B runtime verbatim + 54 B trailer; the solc control
   likewise embeds its 1,621 B runtime at offset 34) and *does* contain the
   `5f3560e01c` dispatcher — yet zero functions are returned. So the
   parsed-empty result is a property of the envelope class, not an absence of
   dispatch bytes in the carrier.
6. **The encoding trap is asymmetric, and the hex parser is stricter than the
   r3 note implies.** `raw` over hex *text* → exit 0, 0 functions, decoded sha
   == the text file's own sha (reproduced on both a solc and a Vyper carrier,
   both pins). The reverse — `hex` over raw *binary* — is a **typed refusal**:
   `invalid_request` / `invalid_input` / `invalid_format`, `"Hex carrier must be
   valid UTF-8."` The hex parser **accepts** `0x` and `0X` prefixes (both parse
   to the same decoded bytes and the same selector set), and **refuses** interior
   whitespace and odd digit counts with `"Hex carrier requires complete
   hexadecimal byte pairs, an optional 0x prefix and outer ASCII whitespace;
   interior separators are invalid."` The r3 entry should be corrected: the
   `0x` prefix is tolerated, not a trap.
7. **Non-bytecode input splits into two declared classes.** *Refused*
   (`invalid_request`, no envelope): missing path (`ENOENT`), directory, symlink
   (`Expected a regular file without a symlink`), `/dev/null`. *Parsed-empty*
   (exit 0, `functions: []`, decoded sha == the file's own sha, no warning in
   `diagnostics`): empty file (0 B, `e3b0c442…`), JSON text, plain text, a
   43 KB ELF executable. Missing/invalid `encoding` is a different error family
   entirely — `VALIDATION_ERROR` with `fieldErrors`, not `invalid_request`.
