### 3.1 Measured deltas vs the r3 solc entries (the round's real content)

1. **A third dispatcher prologue class.** r3 knew `5f3560e01c` (solc) and
   `60003560e01c` (r1 control). Vyper 0.4.3 emits
   `5f3560e01c6002600d820660011b61060001601e395f5156` — the same
   `PUSH0 CALLDATALOAD PUSH1 0xe0 SHR` head, but then a **modulo-indexed jump
   table**: `dest = 0x600 + ((selector mod 13) << 1)`, `CODECOPY` of a 2-byte
   table entry to `MEM[0x1e]`, `MLOAD`, `JUMP`; each bucket holds a chain of
   `PUSH4 DUP2 XOR PUSH2 JUMPI` legs whose shared tail is `0x5e8`/`0x5e9`.
   This is *not* a compare tree and *not* an `EQ` chain. Three buckets (`1`,
   `7`, `11`) are empty and enter that tail directly. **Measured, and correcting
   my own first reading:** the shared tail is the **`__default__` (payable)
   body**, not a revert stub — `0x5e9` decodes as `PUSH1 0x01 SLOAD CALLVALUE
   DUP2 ADD DUP2 DUP2 LT PUSH2 0x05fc JUMPI … SSTORE STOP`, i.e.
   `self.total_deposits += msg.value`. Executing unmatched selectors
   (`00000000`, `ffffffff`, `deadbeef`, `12345678`) walks its bucket's chain,
   takes the `JUMPI 0x5e8` mismatch branch, and lands in that default body.
   `0x5fc` (`JUMPDEST PUSH0 DUP1 REVERT`) is only the arithmetic-overflow
   branch. So an unmatched selector is *payable*, matching the ABI's
   `fallback {payable}` — which is also why `__default__` needs no dispatch leg
   of its own, and why its `method_identifiers` entry has no runtime constant.
2. **`bytecode_offset` semantics differ on this shape.** For solc carriers the
   reported offset is a dispatcher `PUSH2` jump target (a JUMPDEST). Here it is
   the matching leg's **fall-through** — the first instruction of the function
   body — and `runtime[offset]` is *not* `0x5b`. VZ-1's independently derived
   rule (`offset == push4_pc + 11`) is the same fact. The r3 reading "offsets
   land on JUMPDEST" must **not** be applied to this class without restating it.
3. **`raw_result.metadata` is `null` for the Vyper runtime.** The solc carriers
   carry a terminal CBOR trailer (r3 decoded `cborLength 51`, `ipfs` + `solc`).
   Vyper 0.4.3 puts **no trailer in the runtime**; the metadata lives only in
   the *creation* code, after the embedded runtime (55 B here), decoding as a
   CBOR **array(5)** — `[bytes32 ipfs-digest, 1562, [26], 0, {"vyper":[0,4,3]}]`
   — with the trailing 2 bytes a length prefix `0x0037` = 55, and element 2
   equal to the runtime byte length. (solc's is a *map*; Vyper's is an *array*.)
   Any recheck recipe that expects a decoded CBOR trailer on a Vyper runtime
   leg will read `null` — that is correct behavior, not a failure.
4. **`vyper -f method_identifiers` emits a non-ABI key.** It returns 16 entries:
   the 15 ABI functions **plus** `__default__(): 0x89402a72`. That value is a
   real selector (`keccak256("__default__()")[:4]`, re-derived here) but there
   is no such function in the ABI, and `0x89402a72` does **not** occur in the
   runtime bytes (the payable fallback is entered by *failing* all 15 legs).
   A K-derivation that unions `method_identifiers` with the ABI over-counts by 1.
   Separately, vyper strips leading zeros (`0x776076f`, `0xc751377`) — naive
   string comparison against a padded `0x0776076f` silently mismatches.
5. **The `payable` mutability over-read is not Vyper-specific — it reproduces.**
   All 8 arg-taking functions read `payable` (truth: view/nonpayable/pure); all
   7 zero-arg functions read correctly. The byte-level correlate is exact:
   those 8 bodies open with a **fused guard**
   `PUSH1 0x24 CALLDATASIZE LT CALLVALUE OR PUSH2 <revert> JUMPI` at body+4 —
   `CALLVALUE` appears at body+0 only on the one genuinely-payable function.
   Re-measuring the r3 solc carriers with the same recipe shows the same class
   (carrierB 10/11 correct, CarrierB 7/8, VaultB 13/13), so it is an upstream
   inference limitation on this guard shape, not a Vyper defect. The
   `inferred_arguments` field is also lossy: it emits `uint256` for `address`
   and `bytes32` parameters (e.g. `is_owner(address)` → `uint256`).
6. **Zero false positives on decoys (aligned census).** `08c379a0`
   (`Error(string)`) occurs 6× and the ASCII run `69656e74` once; the probe
   reports neither. A naive *unaligned* `PUSH4` regex over-reports `69656e74`
   — that was my own first measurement's artifact (§4, A2), not a probe defect.
