**Terminal-leg orientation (CORRECTION to entry-draft:22).** The last (highest-selector) leg is always a 10-byte fall-through leg (the leading `DUP1` is dropped), but it has two measured forms:

- default block emitted before the dispatch (receive/fallback or reused guard/revert): `PUSH4 <max_sel> SUB PUSH2 <default> JUMPI`, then fall-through into the handler. Measured: `ViaIrVault` opt200 (`…ee02438e 03 61000e 57`, entry 204 = 194+10) and noopt; `Ex11Fallback6` (`…ee919d50 03 61000e 57`, entry 121 = 111+10; default is the **fallback handler at 14**). Entry bytes are not JUMPDESTs (`0x34` opt200 / `0x61` noopt / `0x34` fallback).
- default revert emitted after the dispatch: `PUSH4 <max_sel> EQ PUSH<w> <handler> JUMPI`, then `5f80fd` and the handlers. Measured: `Ex11Linear5` (`…ee919d50 14 610050 57 5f80fd 5b`), `Ex11Twenty` (`…e92cffaf 14 6100f5 57 5f80fd 5b`), `Ex11One` (`…e8174ac8 14 601d 57 5f80fd 5b`). Entry = dst JUMPDEST.

So "SUB-terminated" is **carrier-layout-scoped**, not a class marker. The invariant class marker is the sorted ascending linear scan plus the inverted (`ISZERO`) calldatasize guard.

**Offset convention, generalized.** On EQ-terminal carriers every reported offset is the EQ `PUSH2`/`PUSH1` dst (a JUMPDEST). On SUB-terminal carriers the first `K−1` rows are EQ dsts (JUMPDESTs) and the last row is `push4_pc+10`, the fall-through handler entry (not a JUMPDEST). EX-7's "14/15 + 1" is the K=15 instance of `(K−1)+1`. My `evidence/offset-check.txt` checks every reported offset against the walker on 10 probe legs (15+15+15+15+15+5+6+1+20+6 rows): **exact_match=True on all ten**. Also, at a 109-B runtime the destination is encoded `PUSH1`, not `PUSH2` — the push width is code-size-dependent (entry-draft:22/24 say `PUSH2`; scope note, §5.5).

### 3.3 "Pipeline controls the shape" is K-scoped (CORRECTION)

Entry-draft:23 says "Legacy pipeline: binary search with GT pivots. viaIR: linear scan, sorted, SUB-terminated." My same-source pairs show that the *tree* difference is only visible at larger K:

The `ISZERO` guard does separate them at every measured K: viaIR guard bytes `60043610 15 …`, legacy `60043610 …` (no `15`) on all 11 legs (`evidence/matrix.txt`). The entry's taxonomy sentence should therefore key on the guard + terminal orientation, not on "legacy = binary search" as a universal. ## 5. Corrections, each with evidence and a proposed fix

**5.1 Carrier census (entry-draft:16; source comment `ViaIrVault.sol:5`).** The source has **15** explicit external functions, not 14, plus `receive()`. `methodIdentifiers` has 15 keys; the ABI has 17 entries = 15 functions + 1 constructor + 1 receive; the probe reports 15 functions. `receive()` contributes no selector (it is the calldatasize==0 path), so the sentence "14 explicit + receive = 15 dispatched entries" double-counts the wrong thing. Proposed: "15 explicit external functions + `receive()`; the 15 ABI selectors are the dispatch set (receive is the calldatasize==0 path, no selector entry)." The mutability census view×7/pure×1/nonpayable×6/payable×1 is correct for the 15 functions.

**5.2 Final-leg class (entry-draft:22).** Replace "terminated by a 15th leg in a different opcode class: `PUSH4 ee02438e SUB …`" with: "terminated by the highest selector in a 10-byte fall-through leg; on this carrier that leg is the `SUB` form (`63ee02438e 03 61000e 57`) because the default block precedes the dispatch. Across the six measured legs (five distinct carriers) both terminal orientations occur — `SUB→default` with fall-through entry `push4_pc+10`, and `EQ→handler` with entry = dst JUMPDEST — so the class marker is the sorted linear scan + inverted guard, not the `SUB` opcode." Evidence: §3.2 and `evidence/terminal-legs.txt`.

**5.3 "0 payable-reads" (entry-draft:27).** One function is reported payable — `deposit()` (`d0e30db0`), which is payable in the ABI. The intended claim is true: **0 payable *misreads*** (no ABI-nonpayable function read payable). Proposed wording: "zero payable misreads; the sole payable read is `deposit`, ABI-payable."

**5.4 File count (EX-7.md:62).** "42 files" → **46** (src 1 + scripts 5 + evidence 8 + out 24 + probe 7 + entry-draft 1), measured now.

**5.5 `PUSH2 dst` (entry-draft:22/24).** At the probed 1,517–4,144 B sizes the destination is PUSH2; at my 109-B `Ex11One` the same leg is `63 e8174ac8 14 601d 57` (PUSH1). Proposed: "PUSH2 at the probed sizes; push width is code-size-dependent (PUSH1 observed at 109 B)." Offset semantics are unchanged.

**5.6 Noopt destinations are trampolines (nuance, not an error).** In `viair-noopt` the 14 chain dsts 208–273 are JUMPDEST *stubs* (`5b 61 <target> 56`) one jump from the handler bodies; `viair-opt200`'s dsts 253–982 are handler heads. The entry says "chain dsts 208–273" for noopt (correct) and "handler heads" only for opt200 (correct); a reader should not generalize "handler head" to noopt.

**5.7 Legacy = binary search (entry-draft:23).** See §3.3: true at K=15/20, false at K=1/5/6 (legacy linear EQ, no GT). Proposed: "legacy uses the r3 GT/EQ binary search at K=15/20 on this compiler; at K≤6 both pipelines emit linear EQ chains — the `ISZERO` guard is the pipeline marker at all measured K."

**5.8 r1 class provenance (minor).** The r1 entry's own text names `60003560e01c` only in its Unknowns (`2026-10-19-arc3-r1-evm-real-solc.md:29`); the concrete bytes for the r1 linear control are in the r3 entry's re-probe (`2026-10-19-arc3-r3-evm-optimizer-shapes.md:23`). The taxonomy is supported, but the stronger citation is r3:23.
