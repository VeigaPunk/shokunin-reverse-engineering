# Carrier-guard review (D3)

**Axes:** calibration, coverage, depth. **Scope:** read-only review of the D3 contract, runner-generation criteria, and existing manual-arm record. `W20/tools/carrier-guard.py` and its directory were absent in the reviewed tree (read and directory listing both returned not found), so implementation-level checks of mutation ordering, path handling, record validation, and cleanup were not possible. Findings below distinguish contract-level observations from inference.

## Findings

1. **Medium — chmod affects the owner’s whole install; crash can strand it.** **Observation:** D3 clears exec bits and offers a separate disarm operation to restore recorded modes (contract.md:46-52). The manual record reports `/home/vgpnk/.local/opt/go-1.24.6/bin/go` changed from `0o755` to `0o644` (evidence/carrier-guard/manual-arm.json:6-11). Current stat results show this Go tree and files owned by `vgpnk`; `/home/vgpnk` is mode `700`, so ordinary other UIDs cannot traverse it, but all concurrent jobs/processes under this owner share the changed installation. **Inference:** termination, power loss, or an interrupted multi-file arm before disarm can leave the owner’s Go workflows broken; the contract describes no automatic crash recovery or durable per-file journal. **Smallest remediation:** do not chmod the shared install; arm private disposable carrier copies. If original files must be changed, persist a recoverable journal before each change and provide a separately invoked recovery path.

2. **High for adversarial same-UID use; limited for accidental direct exec — check/use is not an atomic boundary.** **Observation:** the planned runner performs `check` before each label and aborts on exit 1 (gen-wave1.py:267-269); the contract’s selftest proves direct `execve` refusal on a fixture and explicitly excludes loader-mapped execution and root (contract.md:50-52). **Inference:** a check in one process cannot guarantee the later REA launch sees exec-free files: a same-UID process can restore an exec bit or replace a path after check and before launch. The listed ctime/hash checks only attest the instant checked, absent a lock or OS boundary spanning the launch. The owner also owns the files and can chmod them. Thus this is a useful accidental direct-exec guard, not enforcement against a hostile or racing same-UID process. **Smallest remediation:** run from protected private copies owned by a separate, unprivileged worker identity, and perform validation plus launch inside that boundary; don’t rely on a preflight check as the control.

3. **Medium — arm/check/disarm records are not shown to be authentic.** **Observation:** D3 specifies JSON records and checks carrier bytes/modes/ctime, but the contract does not specify signatures or an authenticated append-only store (contract.md:46-49). The visible manual-arm record is ordinary JSON containing editable path/hash/size/mode/ctime claims and a `PermissionError` claim (manual-arm.json:1-11, 166-170); the generated acceptance criterion asks for an arm record and a successful check record with the expected carrier set (gen-wave1.py:69-71). **Inference:** the inspected artifacts alone cannot distinguish an actual check from a rewritten JSON record. A carrier SHA-256 authenticates neither the record nor who performed the check. The absent implementation leaves open whether it validates record schema, path-set binding, or tampering. **Smallest remediation:** treat these JSONs as claims; bind verification to independently recomputed results and a trusted commit/run receipt, or authenticate records with a signer unavailable to the author of the artifacts.
