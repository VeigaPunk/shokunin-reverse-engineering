# H0/H1 semantics and vet field mismatch

## Findings

**Observation — hypotheses.** `swiss-misread.py` defines H1 as binding `internal/abi.OldMapType` for every map, so Swiss descriptors are read 24 bytes early; H0 uses the descriptor's true layout (Swiss for Swiss builds, old for `noswissmap`) (`.ufo/waves/round-18/tools/swiss-misread.py:10-16`; implementation at `:720-725`). These are emulator hypotheses about map-type layout, not two definitions of the full type-markup walk.

**Observation — field contract and implementation.** The emulator separately evaluates each map type under each hypothesis and records map-path failures (`.ufo/waves/round-18/tools/swiss-misread.py:1309-1337,1373-1432`). It then appends the first full-walk EOF/invalid-index to the same per-hypothesis read lists (`:1441-1460`). The explicit comment says `predicted_failure` is the map-path boolean and the full walk is separate; accordingly `predicted_failure_h0` is assigned from the map-path-only `h0_fail` (`:1461-1466`). But `predicted_failure_kind_h0` is calculated from the now-merged EOF/invalid lists (`:1468-1482`), and `diagnostic` compares those kinds (`:1531`). Thus the boolean and kind are not the same predicate: an invalid index found only by the approximate full walk can produce `false` plus `"invalid_index"`.

**Observation — vet.** The prescan has H0 false and H0 kind `invalid_index`; its H0 invalid-index list contains only `1801722468838924630` (`.ufo/waves/round-19/evidence/prescan/kr19-sm-vet.json:2660-2681`). The separate walk record identifies that same index under both H0 and H1 at type `7586208`, with the path ending `func.param[7]` (`:2690-2729`). H1 also has map-path invalid-index entries, while H0's list contains just the walk index (`:2669-2680`). The source therefore explains the discrepancy: the H0 map-path prediction is no failure, but the emulator's full walk separately fails and contaminates the exported H0 kind/read list.

## Bug and frozen-prediction effect

**Conclusion — bug, with scope.** This is a field-semantics/aggregation bug: the documented map-path `predicted_failure_kind_h0` is allowed to include a walk-only failure. The `predicted_failure_h0: false` value itself is consistent with the tool's stated map-path boolean contract. Do not treat the H0 kind as evidence that the H0 map-path failed. The walk failure is an emulator observation, not proof that Ghidra would fail there; the tool itself limits the walk as an approximation at `:1461-1464`.

**Observation — freeze impact.** The round-18 prediction generator directly stores `predicted_failure_kind_h0` as `h0_kind`, stores `diagnostic`, and forms `diagnostic_set_D` from that diagnostic flag (`.ufo/waves/round-18/gen-predictions.py:63-66,73-82`). Mechanical reuse on vet would therefore freeze `h0_kind: invalid_index` and `diagnostic: false`, and omit vet from a D set formed from `diagnostic`, despite the intended H0 outcome being no map-path failure. The R18 decision rule defines the H0 outcome as no Go analysis failure (`.ufo/waves/round-18/predictions/decision-rule.json:7,19`); its existing diagnostic Swiss examples have `h0: none` (`:137-149,183-195`).

The specific R19 instruction instead says D is labels predicted to fail under H1 and says the L1 must freeze (not this prescan seat) (`.ufo/waves/round-19/gen-wave1.py:141-146`). Vet's H1 map-path prediction remains `true` / `invalid_index` (`kr19-sm-vet.json:2663-2668`), so that H1 outcome and its H1 read list do not change. At inspection, the R19 prediction freeze was not yet present; the instruction explicitly leaves it to L1. **Answer:** yes, the bug would change the frozen H0-kind/diagnostic-derived fields, and could wrongly remove vet from a mechanically reused R18 D set; it does not change the H1 expected outcome. Under R19's explicit H1-failure D definition, the correct freeze should include vet in D and preserve H0 as no map-path failure, rather than copying the contaminated H0 kind.

**Inference — likely mechanism.** The walk-only vet index comes through a non-map `func.param[7]` route (`kr19-sm-vet.json:2700-2711,2717-2728`); because the field-merging code explicitly appends walk invalid indexes (`swiss-misread.py:1454-1460`), it is sufficient to explain the mismatch. Whether the same failure would occur in Ghidra is not established by this emulator output.
