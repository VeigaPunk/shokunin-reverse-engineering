# C3 run-plan simplification

## Axes
- **Calibration:** retain one frozen H1-positive and one H1/H0-silent control.
- **Depth:** distinguish that minimal test from the broader eight-carrier coverage claim.
- **Freshness:** keep carrier digests and predictions frozen before any measured Ghidra run.

## Findings

**Observation — current scope.** C3 names the Go 1.25.0 toolchain executables `go`, `gofmt`, `asm`, `cgo`, `compile`, `cover`, `preprofile`, and `vet`; `link` lacks Go build info. The prescan summary calls `vet` H1 `invalid_index`, `link` unparseable, and the other seven silent (`.ufo/waves/round-19/contract.md:41-44`; `claims.json:26-28`). Do not count `link` as a silent control: its record is explicitly `status: unparseable` with “no Go build info” (`evidence/prescan/kr19-sm-link.json:1-4`).

**Inference — minimum for a binary H1/H0 test.** Run `vet` plus one silent control, not all seven. `vet` is the required positive: the prescan shows three map types with H0 `silent` / H1 `invalid_index` (`evidence/prescan/kr19-sm-vet.json:26-45`), and H1 predicts reads `[13902080, 852107777, 1801722468838924630]` versus H0’s `[1801722468838924630]` (`…/kr19-sm-vet.json:2663-2680`). Use `preprofile` as the economical nontrivial negative: 30 map types, 3 misread map types, but H0/H1 both predict no failure and no invalid-index reads; its carrier is 2,274,474 bytes (`evidence/prescan/kr19-sm-preprofile.json:21-47,577-585`). The other six predicted-silent inputs (`go`, `gofmt`, `asm`, `cgo`, `compile`, `cover`) are run-plan deletion candidates for this minimal experiment, not files or provenance to delete. `compile` is a stronger optional stress control (297 map types, 15 misreads, 21,518,237 bytes; `…/kr19-sm-compile.json:21-47`), but adds breadth/cost rather than a necessary second hypothesis outcome.

**Important calibration caveat.** Do not use the `vet` top-level `diagnostic:false` as its selection criterion: its per-type `diagnostic_detail` has three H0/H1 differences, and `predicted_failure_h1=true` while `predicted_failure_h0=false` (`…/kr19-sm-vet.json:26-45,2663-2668`). Both aggregate `predicted_failure_kind` fields nevertheless say `invalid_index`, because the common walk-only invalid index is included in the read lists (`…/kr19-sm-vet.json:2674-2680,2690-2729`; emulator logic `.ufo/waves/round-18/tools/swiss-misread.py:1413-1439,1454-1482,1531-1532`). The actual discriminator is exact observed read-list equality, not “any analyzer error” versus “no analyzer error”; the existing comparator supports exact `invalid_index_reads` equality (`.ufo/waves/round-17/tools/compare.py:212-216`). R18’s prose rule says an H0 outcome is “no Go analysis failure” (`.ufo/waves/round-18/predictions/decision-rule.json:7,19`), which is too coarse for this prescan: its full walk records the shared failure under both hypotheses. Freeze a R19 rule that distinguishes the H1 list from the H0 list; do not classify `vet` from the boolean `diagnostic` field.

**Scope tradeoff.** The two-carrier set discriminates this Go 1.25.0 toolchain sample under the stated emulator outcomes; it does not establish silence across all seven controls. The existing C3 claim describes per-carrier outcomes and says `k` is the number run (`claims.json:26-27`): report `k=2`, retain all unrun predictions as unobserved, and avoid an eight-carrier or population-wide claim. Also, these are Go toolchain executables, not application ELFs (contract lines 41-42), so the “application ELFs” phrasing in `claims.json:26` is not supported by this carrier list.

## Can R18 runner be used with env overrides only?

**No for the required R19 output and run contract; yes for most of the pipeline.** R18 already accepts a predictions-directory override and its fourth TSV column is used as a digest for non-`synthetic-*` rows (`.ufo/waves/round-18/run-carriers.sh:24-29,224-243`), which fits the R19 toolchain rows if their kind is non-synthetic. The carrier tool’s default REA package is already pinned to `rea-agents@6.5.0` (`.ufo/waves/round-17/tools/carrier-run.py:288-293,352,731-750`).

But R18 hard-codes `W` to round 18 (`…/round-18/run-carriers.sh:20`) and permits output only under `$W/runs/` or `/tmp` (`…/round-18/run-carriers.sh:208-215`). `RUNS_DIR=/.../round-19/runs` therefore fails the guard; `/tmp` would not meet the retained-output path. R18 also requires a separate `SUMS` file at preflight and reads that file for synthetic rows (`…/round-18/run-carriers.sh:28-29,174-181,224-235`), while R19’s task specifies the TSV digest as the hash source (`.ufo/waves/round-19/gen-wave1.py:147-152`). Finally, R18 passes a fixed `--timeout 1500` with no timeout override (`…/round-18/run-carriers.sh:269-273`); R19 explicitly requires a per-carrier timeout choice based on the retained R18 timings and 2–22 MB sizes (`gen-wave1.py:149-152`).

R19 prediction generation also records `link` as excluded (`gen-wave1.py:141-145`). If that exclusion is represented as a TSV row, R18 ignores its extra field and will either try to run it or fail it for a missing prediction (`round-18/run-carriers.sh:204-207,217-223`); keep the exclusion record, but explicitly skip it or keep it outside the runnable TSV. Minimal adaptation: set the wave root/output guard for W19, use each runnable row’s TSV SHA-256 as the single carrier-digest authority, preserve the exclusion as data without treating it as a run, and set the required timeout policy. Keep the existing pin/log/compare flow and selftest structure.
